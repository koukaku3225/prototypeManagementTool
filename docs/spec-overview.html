01何を検証するのか

MVPは製品の縮小版ではなく、仮説の検証装置。作る範囲は検証したいことから逆算して決める。

#仮説判定方法
H1AIとの構造化対話は、自力でワークシートを埋めるより深い目標設定ができる目標カードの「意味づけ」欄の記述量と具体性
H2「なぜ」を掘る対話は、外発的・回避的な動機を内発的動機に変換できるフェーズ2→3で motivationType が変化した割合
H3疑似人格への「約束」は、翌日の実行率を上げる約束ステップあり／なしのA/B比較
H4意図的な待ち時間はユーザーの回答の質を上げる待ち時間あり／なしで回答文字数と具体性を比較
最優先

H1が偽なら、この先の記録・振り返り・リマインダー機能を作る意味がない。MVPはH1の検証装置であるという一点が、以降のすべての取捨選択の基準になる。

02設計の分岐点

仕様を固める過程で8つの分かれ道があった。採用しなかった案も、判断の根拠とともに残しておく。前提が変われば選び直せるようにするため。

01自己分析をどう扱うか
見送り — 独立モード
性格診断と時間軸の整理を独立した画面として先に置き、その結果を目標設定に渡す。 診断を先にやらせると、目標に辿り着く前に離脱する。「何のためにこれを答えているのか」が見えない時間が長すぎる。
採用 — 対話に溶かす
独立モードを作らず、目標設定対話の中でAIが価値観・生活パターン・過去の挫折を聞き出し、裏で UserProfile に蓄積する。 ユーザー体験は「目標を決めに来た」のまま。自己分析は副産物として溜まり、2回目以降の対話品質を上げる。
02対話をどこまで作るか
見送り — フェーズ1〜3のみ
動機の変換までで打ち切る。SMART化とWBSはフォームでも書けるので作らない。 実装は最短。ただし成果物が抽象的なままで、「明日の一歩」が出ない。H1の判定材料が弱くなる。
採用 — フェーズ1〜5フル
発散から明日の1タスクまで通しで対話する。 対話の価値は「抽象が具体に変わった」体験にある。終点まで届かないと検証にならない。
03待ち時間の粒度
採用 — セッション内60秒ロック
フェーズ2・3の「なぜ」の問いに限り、送信ボタンを60秒ロックする。入力欄は開いたまま。 1回のセッション内で完結するので、A/B比較がすぐ回る。スキップボタンは置かない（置けば必ず押される）。
見送り — 24時間ロック
目標カードの確定を翌日まで待たせ、「まだこれで良いか」と再確認する。 効果は大きそうだが検証サイクルが1日単位になる。将来の拡張案として保留。
04AIモデルの構成
見送り — 全ターン同一モデル
対話も構造化もすべて claude-haiku-4-5 で通す。 最も安いが、構造化抽出を誤ると目標カード全体が壊れる。壊れたカードはH1の検証を汚染する。
採用 — 2段構え
対話ターンは claude-haiku-4-5、構造化抽出と動機判定だけ claude-sonnet-5。 呼び出し回数の多い対話を最安に抑え、失敗コストの高い箇所だけ上位モデルに払う。1セッション約20〜25円。
05「約束」のUI
見送り — ボタンで同意
「約束する」ボタンを1つ置いて押させる。 実装は簡単だが、押す行為に体重が乗らない。同意の言葉が残らないので翌日に再提示できない。
採用 — 自分の言葉で打つ
テキスト入力欄を出し、ユーザー自身の言葉で答えさせる。打たれた言葉を保存し、翌日ホーム画面で再提示する。 自分の言葉を書く行為がコミットメントを強くする。H3の検証装置そのもの。
06扱う目標の数
見送り — 複数目標＋優先順位づけ
目標リストを作り、重要度を定数化して選ばせる。 検証対象がぼやける。そもそも構想上も「基本は一つの目標に固定する」としている。
採用 — 1目標固定
1セッション＝1目標。優先順位づけの機能は作らない。 対話の深さに集中できる。目標同士の依存関係グラフも自動的に不要になる。
07If-Thenプランの置き場所
見送り — 独立した機能
予防プランを作る専用の画面とデータ構造を用意する。 実装が増える割に、目標と切り離されたプランは使われない。
採用 — WOOPのPlanに統合
フェーズ5でWOOPの障害と対策を作る流れに含める。 WOOPのPlanがIf-Thenそのもの。新規実装ゼロで差別化機能が入る。
08データの永続化と外部連携
見送り — 認証＋サーバーDB＋Notion連携
ログインを作り、サーバーに保存し、Notionをデータベースとして繋ぐ。 検証に必要ない実装が大量に増える。Notion連携は仕様が固まる前に繋ぐと作り直しになる。
採用 — localStorage＋エクスポート
ブラウザに保存し、JSON／Markdownでダウンロードできるようにする。 手で貼れば検証には足りる。エクスポート機能が将来のNotion連携の足場にもなる。

03画面と流れ

画面は4つ。すべてスマホ幅固定（max-w-[420px]）で、PCブラウザで開いても実機幅で表示される。

コーチ人格

選んだ1人格を全ターンで固定し、途中で変えない。口調の差が体感できることが最低条件になる。

ID名前性格口調の例
kaedeカエデ伴走型・共感重視それ、すごく大事なことだと思います。もう少し聞かせてください
rinリン厳しめ・直球今の答え、抽象的すぎませんか。具体的にどういうことですか
souソウ淡々・分析型整理すると、3つの要素がありますね。順に見ていきましょう

045フェーズ対話

抽象的な願望から、明日45分でできる作業まで降りていく。フェーズ番号は画面に出すが、フェーズ名は出さない（構えさせないため）。

フェーズごとのAIへの指示

各フェーズのプロンプトは「やること」と「やってはいけないこと」の対で書く。禁止事項の方が効く。

1発散diverge 3〜5ターン上限6
やるオープンな問いを1つだけ投げる。ユーザーの言葉をそのまま受け止める。「それは具体的にはどういう状態ですか」と情景を聞く
やらない要約しない。評価しない。「それはいい目標ですね」と賞賛しない。期限や数値をこの段階で聞かない
2意味の掘り下げmeaning 中核60秒ロック5〜8ターン上限10
やる「なぜそれが大事なんですか」を表現を変えて3回。2回目以降は直前のユーザーの言葉を引用して問う。詰まったら待つ
やらない答えを誘導しない。「つまり◯◯ということですね」で締めない。3回未満で次に進まない。心理学用語を出さない
3動機の変換reframe 60秒ロック2〜5ターン上限6
判定internal「やりたい・面白い」／external「評価されたい・昇進のため」／avoidance「怒られたくない・取り残されたくない」
やる断定せず確認する →「では、評価されたその先で、何ができるようになっていたいですか」と一段先を問う
やらない言い換えを押しつけない。「評価されたいこと自体が目的です」と本人が言えば、それを尊重して次へ進む
4具体化smart 4〜7ターン上限9
やる数値が曖昧なら「週1回? 毎日?」と選択肢を出す。期限が1年以上先なら手前に確認地点を作るよう提案する
やらない目標をユーザーの代わりに決めない。4要素を一度に聞かない
5障害と行動woop_wbs 4〜6ターン上限8
やるつまずく状況を特定 → 「もし〇〇になったら××する」の形に変換 → 作業を3〜5個挙げさせ「明日45分以内でできるもの」を1つ選ばせる
やらない障害を代わりに考えない。ユーザーの生活を知っているのはユーザー。タスクを2つ以上出さない
堂々巡りの防止

フェーズ遷移の判定は対話生成と同じAPI呼び出しで行い、応答末尾の <<<PHASE:meaning>>> をクライアント側で剥がす（追加コストなし）。加えて各フェーズに最大ターン数を設け、超えたらシステム側で強制遷移する。

共通コーチング原則（全フェーズ）

あなたはコーチであり、コンサルタントでもセラピストでもない。

- 答えはユーザーの中にある。あなたは問うだけ
- 1つの発言につき、質問は1つだけ
- ユーザーの言葉をあなたの言葉に置き換えない。そのまま使う
- 沈黙を埋めない。短い返答でも催促しない
- 助言をしたくなったら、代わりに問いにする
- 1発言は3文以内。長い説明をしない
- 診断名や心理学用語を使わない

05対話が残すもの

1回の対話から2つの成果物が出る。片方はユーザーに見せ、片方は見せずに次回へ持ち越す。

GoalCard の型（抜粋）

export interface GoalCard {
  vision:  { raw: string; refined: string };

  meaning: {
    whyChain: string[];              // 「なぜ」3階層の答え
    values: string[];                // 抽出された価値観キーワード
    motivationType: "internal" | "external" | "avoidance";
    reframed: string | null;         // 変換後の表現
    reframedFrom: string | null;     // 変換前の表現
  };

  smart:   { specific; measurable; metricTarget; deadline; achievableNote };

  woop: {
    outcome: string;
    obstacles: {
      text: string;                  // 「帰宅後に疲れて手が止まる」
      situation: string;             // 「平日21時以降、帰宅直後」
      plan: { if: string; then: string };
    }[];
  };

  tasks: Task[];                     // MVPでは常に1件

  commitment: {
    accepted: boolean;
    userWords: string | null;        // ユーザーが実際に打った同意の言葉
  };
}
抽出プロンプトの最重要制約

ユーザーが言っていないことを補完しない。情報が不足している項目は推測せず null にする。

AIが勝手に立派な目標を作ると、ユーザーは「自分の目標」だと感じられなくなる。そうなるとH1の検証そのものが汚染される。refined は raw の言い換えであって、内容を足してはいけない。

06AI構成とコスト

呼び出し回数が多いところを最安に、失敗コストが高いところに上位モデルを払う。

モデルInput / 1MOutput / 1Mコンテキスト用途
claude-haiku-4-5$1.00$5.00200K対話の各ターン
claude-sonnet-5$3.00$15.001M構造化抽出・動機判定
claude-opus-5$5.00$25.001M予備（品質が足りない場合）
キャッシュの落とし穴

プロンプトキャッシュはプレフィックス一致。システムプロンプトに時刻や乱数が混ざると毎回失効する。usage.cache_read_input_tokens が0のままなら、どこかに揮発値が紛れている。

08検証指標

4つの仮説を判定するために、対話中とその翌日に取るデータ。

#指標取得方法目安
M1対話完走率completedAt != null の割合60%以上
M2離脱フェーズ分布中断時の currentPhase特定フェーズに集中していないか
M3フェーズ2の滞在時間タイムスタンプ差分8分以上
M4フェーズ2の回答文字数content.length待ち時間あり > なし
M5目標カードの編集箇所編集された項目のログ編集率50%超は要改善
M6動機タイプの変換率reframedFrom != null の割合50%以上
M7翌日タスク実行率task.completedAt != null約束あり > なし

M7が最重要指標。ただし翌日の追跡にはユーザーの再訪が必要なので、テスト参加者には事前に「明日もう一度開いてください」と伝える運用にする。

09未決事項

実装に入る前に決める必要がある4点。

  1. テスト参加者の集め方自分1人で回すのか、5〜10人に依頼するのか。M7（翌日実行率）の比較には最低5人ほしい。人数が確保できないなら、A/Bをやめて全員に約束ステップを出す設計に変える。
  2. コーチ選択を必須にするか選択を必須にすると最初の一歩が重くなる。kaede を既定にして「変更できます」と添えるだけでもいい。
  3. フェーズ2の逃げ道現仕様では「なぜ3回」をスキップできない。テストで離脱がここに集中したら緩和が必要になるが、緩和すると価値の中心が薄まる。どこまで粘るかの線引き。
  4. 目標カードのビジュアル投資現仕様はテキスト中心。「愛着が湧くカード」にするデザイン投資をするかは、H1の検証後の判断でよい。
