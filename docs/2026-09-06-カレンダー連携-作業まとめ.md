## 1. 何を作っているか

タイムボックス（時間割）とGoogleカレンダーを、**タイトルと時間だけ**双方向に同期する。

- アプリで枠を作る → カレンダーに出る
- カレンダーで予定を入れる → アプリの時間割に出る

### 決めたこと（設計の要点）

| 論点 | 決定 | 理由 |
|---|---|---|
| 同期の対象 | アプリが作った**専用カレンダーだけ** | 仕事の会議が時間割に流れ込まない。事故の範囲も限定される |
| 反映の早さ | **アプリを開いたとき**＋手動更新 | 定期実行やプッシュ通知の仕組みを増やさない |
| カレンダーで削除されたら | **振り返り等が空なら消す。何か書いてあれば残す** | 書いたものが黙って消えない |
| Googleの権限 | `calendar.app.created`（アプリが作ったカレンダーのみ） | 本来のカレンダーに構造上アクセスできない |
| トークンの持ち方 | 自前OAuthで `refresh_token` を取得し、通常のRLSで保管 | Supabaseは `provider_token` を更新しないため、ログイン相乗りでは1時間で切れる |
| ログインとの関係 | **切り離す**（自前のOAuth往復） | 既存のログイン処理に触らない |

### 却下した案

- **ログインのスコープに相乗り**: Supabaseは `provider_token` を自動更新しない。約1時間で切れ、頻繁に再ログインを強いる
- **ブラウザから直接Google APIを叩く**: 同じトークン寿命の問題。`client_secret` を使えず自前更新もできない

### 増える秘密はゼロ

`GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` は既に `.env.local` にある（Supabase用の控え）。それをそのまま使う。

## 3. レビューで見つかった重大な問題

このやり方（タスクごとに実装→別エージェントがレビュー）の価値が、はっきり出た。

### Task 6 で Critical 4件

**すべて、計画（＝私が書いた設計）の欠陥。実装者は忠実に転記していた。**
そして**4件とも、型チェックでも `npm test`（325件）でも一切現れなかった。**

#### ① 同期のたびに予定が増殖する

差分取得（`syncToken`）は「変更のあった予定だけ」を返すのに、エンジンはそれを
「期間内の全予定」として突き合わせていた。2回目以降、変更の無い枠がすべて
「カレンダーに存在しない」と判定され、毎回新規作成される。10回同期すれば10倍。

→ 差分取得をやめ、毎回全件取得にした。

#### ② 本番でだけ時刻が9時間ずれる

`new Date().getHours()` はサーバーのタイムゾーンを見る。Vercelは既定でUTCなので、
JST 10:00 の予定が 01:00 になる。**ローカル（JST）では絶対に再現しない。**

→ `Intl.DateTimeFormat` に `timeZone:"Asia/Tokyo"` を明示する形にした。

#### ③ 取り込んだ予定が二重取り込みされる

第2ループのスキップ条件が印（timeboxId）経由しか見ておらず、`googleEventId` 経由で
対応づいた予定が漏れる。人がカレンダーで作った予定が同期のたびに増える。

→ 第1ループで処理した event.id を Set に集め、第2ループで参照する形にした。

#### ④ 期間外の枠が毎回重複作成される

取得期間（-7日〜+60日）で `boxes` を絞っていなかった。範囲外の枠は対応する予定が
見つからず毎回新規作成され、作られた予定は範囲外なので次回も見えない。

→ `runSync` の冒頭で同じ期間に絞るようにした。

#### 根本原因

**エンジンにテストが1件も無かった。** だから4件とも素通りした。
→ 依存注入（`SyncDeps`）を入れ、5件のテストを追加（実行して通ることを確認済み）。

### Task 3 で Important 2件

こちらも計画の欠陥。`deleteLink` / `updateLink` / `loadLink` が
**失敗を黙って握りつぶして「成功したように見せる」**形だった。

特に `deleteLink` は連携解除（＝Googleへのアクセス権の破棄）なのに、
DB削除が失敗しても「解除しました」と表示される作りだった。

→ 成否を返す・ログに残す・「未連携」と「取得失敗」を分ける形に修正済み。

## 5. 私が本人に代わって決めたこと（裁定の一覧）

### 実行前のスキャンで見つけた矛盾

**① `STATE_COOKIE` をルートファイルから export していた**
→ `src/lib/calendar/oauth-state.ts` に切り出した。
理由: Next.js はルートの export 面を検証する。ルート同士が互いを import するのも不健全。
**外した場合の損失**: 型チェックが通らず1往復増えるだけ（実装は同じ）

**② 送信件数の上限が本文サイズ上限と矛盾していた**
→ `boxes` の上限を 2000 → 500 に下げた。
理由: 2000件は約300KBで `MAX_BODY_BYTES`（200KB）を超え、必ず413で弾かれる。
**外した場合の損失**: 予定が500件を超える人が同期できない（現状の利用では起きない）

### Task 3 のレビュー指摘に対して

**指摘を全面的に受け入れた**
理由: 仕様書§7が「失敗を黙って通さない」を原則に置いているのに、計画のコードが守っていなかった。
**外した場合の損失**: 連携解除が失敗しても伝わらず、Googleへの権限が残り続ける

**`loadLink` はクエリ失敗時に throw し、null は「未連携／未ログイン」に限定する**
理由: 区別できないと通信障害時に「連携してください」と誤案内する。
**外した場合の損失**: Task 7 の status ルートで未捕捉例外が500になる
→ 対策として Task 7 に「try/catch で包む」を申し送り済み

**Minor（コメント追加）を同じ修正に同梱した**
理由: 同じファイルを開いている最中の1行で、規約の「なぜを書く」に沿う。
**外した場合の損失**: ほぼ無い

### Task 6 のレビュー指摘に対して

**C-1: 差分取得をやめ全件取得にする**
理由: 仕様書は差分取得を指示しているが、仕様書自身の不変条件（データを失わない・壊さない）が
最適化より上位。67日窓・少件数なので全件取得で問題ない。
**外した場合の損失**: API呼び出しがやや増える（実利用では無視できる）

**C-2: `Intl.DateTimeFormat` で JST を明示する** —
**外した場合の損失**: 本番でのみ時刻が9時間ずれる

**C-3: 処理済み event.id を Set で管理する** —
**外した場合の損失**: 人がカレンダーで作った予定が毎回増殖する

**C-4: `boxes` を取得期間に絞る** —
**外した場合の損失**: 範囲外の枠が毎回重複作成され、次回も見えない

**I-5: 依存注入を入れてエンジンのテストを5本追加する**
理由: テストが1件も無く、C-1〜C-4 は型チェックでも npm test でも現れなかった。
直したことを確認する手段が無いままマージはできない。
**外した場合の損失**: 同じ穴が再発しても誰も気づけない

**I-1〜I-4 と Minor も併せて修正**
（失敗の握りつぶし・入力検証・日跨ぎ・印の横取り・`requireAuthIfEnabled` の位置）
