## 1. 前提 — 4種類の入力トークンと、10倍以上の単価差

コストの話をする前に、課金の単位を揃えます。1回のAPI呼び出しで課金されるトークンは4種類あり、単価がまったく違います。

| 種類 | usage のフィールド | 単価（入力の定価を1とする） |
|---|---|---|
| 通常の入力 | `input_tokens` | 1 |
| キャッシュ読み出し | `cache_read_input_tokens` | **0.1** |
| キャッシュ書き込み（5m） | `cache_creation_input_tokens` | 1.25 |
| キャッシュ書き込み（1h） | 同上 | 2 |
| 出力 | `output_tokens` | モデルによる（haiku 5 / sonnet 5倍） |

ここから2つの帰結が出ます。

**帰結A: 「入力トークン合計」を見ても改善したか分からない。**
合計が同じでも、内訳が `input:5000` なのか `cacheRead:5000` なのかで金額は10倍違います。
だから施策7では、合計ではなく必ず4つに分けて記録しています（[src/types/goal.ts](../src/types/goal.ts) の `TokenUsage`）。

**帰結B: キャッシュの損益分岐は「2回読めるか」。**
1hキャッシュは書き込みに定価の2倍かかります。書いて1回も読まなければ、素直に送るより **2倍の損** です。

```
n 回読む場合のコスト（定価を1とする）
  キャッシュあり: 2.0 + 0.1n
  キャッシュなし: 1.0 + 1.0n
  → 2.0 + 0.1n < 1.0 + 1.0n を解くと n > 1.11
```

つまり**同じプレフィクスを2回以上使うなら黒字**。対話は同じシステムプロンプトを10回以上使うので、条件は余裕で満たします（満たすはずでした。第4章参照）。

## 2. なぜ会話履歴のコストは O(n²) で伸びるのか

APIはステートレスです。サーバは前のターンを覚えていないので、**毎ターン、会話の全履歴を送り直します**。

ターン $k$ の入力トークン数を考えます。システムプロンプトを $S$、1往復あたりの平均トークンを $m$ とすると、

$$
\text{ターン}k\text{の入力} = S + km
$$

セッション全体（$N$ ターン）の入力トークン合計は、

$$
\sum_{k=1}^{N}(S + km) = NS + m\frac{N(N+1)}{2} \approx NS + \frac{mN^2}{2}
$$

**履歴の項が $N^2$ で効く**のがポイントです。このアプリの small モードは最大14ターン、$S \approx 1{,}300$、$m \approx 130$ なので、

- システムプロンプト分: $14 \times 1{,}300 = 18{,}200$ トークン
- 履歴分: $130 \times 14^2 / 2 \approx 12{,}700$ トークン

合計で約31,000トークン。**同じ内容を何度も送り直しているだけ**の分が、この大半を占めます。
ここを潰すのがプロンプトキャッシュです。

## 3. プロンプトキャッシュは「プレフィクスの一致」でしか効かない

ここが設計上いちばん大事な性質です。

キャッシュは**プロンプトの先頭から、指定した境界までの塊**に対して働きます。
先頭から1トークンでも違えば、それ以降は全部キャッシュミスです。ハッシュの一致判定だと考えると分かりやすい。

```
[原則][人格][大きな物語][プロフィール] | [フェーズ指示] | [履歴...] | [今回の発言]
 ←────────── 境界① ──────────→ ←─ 境界② ─→          ←─ ③ ─→ ←─ ④ ─→
```

この並びは偶然ではなく、**変わらないものほど手前に置く**という制約から決まります。

- `[原則]` `[人格]` … セッション中ずっと不変
- `[プロフィール]` … 前回のセッションで確定済み。今回は変わらない
- `[フェーズ指示]` … フェーズが変わるときだけ差し替わる（2〜10ターンに1回）
- `[履歴]` … 毎ターン伸びる

もし `[フェーズ指示]` を `[原則]` より前に置いてしまうと、フェーズが変わるたびに**その後ろ全部**（原則も人格もプロフィールも履歴も）がキャッシュミスになります。並び順だけでコストが数倍変わります。

### 変更前のコードの何が問題だったか

```ts
// 変更前
system: [
  { text: COACHING_PRINCIPLES },
  { text: coach.persona },
  { text: renderBigStory(...) },
  { text: renderProfile(...), cache_control: { type: "ephemeral" } },  // ← 境界はここだけ
  { text: instructionsFor(...) },      // 境界の外
],
messages: body.messages,                // 境界の外。毎ターン伸びる
```

境界が system の途中に1つしかありません。つまり**キャッシュ対象になり得たのは全体の3分の1程度**で、

- `[フェーズ指示]`（約1,000トークン）… 同じフェーズを繰り返す2〜10ターンのあいだ、毎回定価
- `[履歴]`（最大2,000トークン超）… 毎ターン全部が定価

が丸ごと定価のままでした。前章の $N^2$ の項が、そのまま請求されていたわけです。

### 変更後

境界は最大4つ打てます。使い切ります。

```ts
// src/lib/chat-prompt.ts
export function buildSystem(body: ChatRequest): Anthropic.TextBlockParam[] {
  return [
    { type: "text", text: COACHING_PRINCIPLES },
    { type: "text", text: coach.persona },
    ...(body.mode === "small" ? [{ type: "text", text: renderBigStory(body.bigStory) }] : []),
    { type: "text", text: renderProfile(body.profile), cache_control: CACHE },   // 境界①
    { type: "text", text: instructionsFor(body.mode, body.phase), cache_control: CACHE }, // 境界②
    ...(isFinalTurn(body) ? [closingInstruction] : []),   // 最終ターンだけ。境界の外
  ];
}
```

履歴側は、**最後の2つの発言**に境界を打ちます。

```ts
export function toCachedMessages(msgs) {
  const marks = new Set<number>([src.length - 1]);   // 境界④ 今回ぶんを書き込む
  if (src.length >= 3) marks.add(src.length - 3);    // 境界③ 前ターンが打った位置
  ...
}
```

なぜ `length - 3` なのか。ターン $N$ のリクエストは

```
[... u(N-1)] [a(N-1)] [u(N)]
      ↑                  ↑
   length-3           length-1
```

という形をしています。`u(N-1)` は、**前のターンが末尾として境界を打った、まさにその位置**です。
だからここが読み出しの当たり所になる。境界④で書いたものを、次のターンが境界③で読む、というバケツリレーです。

これが成立すると、毎ターン定価で払うのは `a(N-1) + u(N)`（差分の約250トークン）だけになり、$N^2$ の項が消えます。

## 4. 実測 — 4096トークンの壁

ここで実際にAPIを叩きました。結果は「まったく効かない」。

```
1ターン目   定価  1794  読     0  書     0  命中率 0%
2ターン目   定価  1842  読     0  書     0  命中率 0%
```

境界は正しく送られています（リクエストを出力して確認済み）。エラーも出ていません。ただ、無視されている。

原因を切り分けるため、システムプロンプトの長さだけを変えて閾値を二分探索しました。

| プロンプト合計 | `cache_creation_input_tokens` |
|---|---|
| 1,334 | 0 |
| 2,104 | 0 |
| 3,314 | 0 |
| 3,760 | 0 |
| 3,936 | 0 |
| 4,024 | 0 |
| **4,112** | **4,101** |

**`claude-haiku-4-5` は、プロンプト合計が 4,096 トークンを超えないと `cache_control` を黙って無視します。**

そしてこのアプリの1ターンは、

| | トークン |
|---|---|
| システムプロンプト（原則＋人格＋大きな物語＋プロフィール＋フェーズ指示） | 約1,300 |
| 履歴（8往復まで積んだ状態） | 約1,050 |
| **合計** | **約2,350** |

上限の14ターンまで対話しても、3,000トークン台に届くかどうか。**閾値の4,096に一度も到達しません。**

### なぜ気づけなかったのか

3つ重なっています。

1. **無視されてもエラーにならない。** 400も警告も返らない。成功レスポンスが返る
2. **日本語のトークン効率を見誤っていた。** `wc -m` はロケール次第でバイト数を返す。UTF-8の日本語は1文字3バイトなので、**文字数を3倍に見積もっていた**。「システムプロンプトは3,500トークンくらいある」は、実際には約1,300だった
3. **usage を捨てていた。** サーバは `cache_read_input_tokens` を返していたし、SSEの `done` イベントでクライアントにも送っていた。しかし受け取り側の `onDone` が `phase` と `forced` しか読んでおらず、**キャッシュが効いているかどうかの唯一の証拠を、毎ターン捨てていた**

この3つ目が施策7そのものです。順番を間違えました。**計測を先に入れていれば、施策1と2に手をつける前に「効かない」と分かっていた。**

### 効かないコードを残した理由

[src/lib/chat-prompt.ts](../src/lib/chat-prompt.ts) の境界指定は残してあります。

- 発動しないあいだの追加コストは **ゼロ**（無視されるだけ）
- プロンプトが伸びれば（人格の追記、長い対話、履歴を要約せず持つ設計変更）**自動的に効き始める**
- 効く条件と実測値をコメントに残せば、次に触る人が同じ探索を繰り返さずに済む

消すのではなく、**発動条件を書いた状態で置いておく**という判断です。

## 5. 施策7 — 計測を先に入れる

今回の教訓を仕組みにしました。

**サーバ側** — 4種類を分けて返す。

```ts
// src/app/api/chat/route.ts
usage: {
  at: new Date().toISOString(),
  model: CHAT_MODEL,
  kind: body.phase,
  input: final.usage.input_tokens,
  output: final.usage.output_tokens,
  cacheRead: final.usage.cache_read_input_tokens ?? 0,
  cacheWrite: final.usage.cache_creation_input_tokens ?? 0,
}
```

**クライアント側** — セッションと同じ場所に貯める。画面のstateだけで持つと、確定前に離脱したセッションのぶんが落ちます。

```ts
// src/hooks/useConversation.ts
...(usage ? { usage: [...(working.usage ?? []), usage] } : {}),
```

**計測画面** — 金額そのものより、**キャッシュ命中率**と**反実仮想との差**を出します。

```
M8 トークンとコスト
  10.1 円 / セッション（1本の平均）
  合計                 10.1 円
  キャッシュ命中率       28%
  キャッシュで浮いた額    0.54 円
  入力（定価 / 読 / 書）  10218 / 4100 / 200
  出力                  3193
```

「浮いた額」は、`cacheRead` と `cacheWrite` のトークンを**すべて定価の入力として数え直した金額**との差です（[src/lib/pricing.ts](../src/lib/pricing.ts) の `usdWithoutCache`）。
キャッシュが効いているかは、この反実仮想と比べる以外に見る方法がありません。

単価表は手で書いた値で、公式の改定には追随しません。**目的は絶対額を当てることではなく、施策の前後で比べること**なので、それで足ります。

## 6. 施策4 — 同じ対話ログを2回送らない

対話の最後に、ログから成果物（目標カード / 大きな物語）と**ユーザープロフィール**を抽出します。ここは sonnet を使っています。

変更前は、この2つを**別々の呼び出し**にしていました。

```ts
// 変更前
const [cardRes, profileRes] = await Promise.all([
  client.messages.parse({ system: STRUCTURE_EXTRACTION_PROMPT,  messages: [{ content: transcript }], ... }),
  client.messages.parse({ system: PROFILE_EXTRACTION_PROMPT,    messages: [{ content: transcript }], ... }),
  //                                                                        ↑ 同じログをもう一度
]);
```

対話ログは約1,000トークン。プロフィール抽出のプロンプトが約900トークン。**約1,900トークンを、プロフィール3項目を取るためだけに sonnet へ余分に払っていました。**

「並列だからキャッシュで安くならないか」とも考えましたが、なりません。**1回目の書き込みが終わる前に2回目が飛ぶ**ので、読める状態になっていない。逐次にすれば読めますが、それは待ち時間を2倍にしてトークンを節約する取引になります。

そこで**スキーマに相乗り**させました。

```ts
// src/lib/structure-schema.ts
export const ProfileFields = {
  profile: z.object({
    lifePatterns: z.array(z.string()),
    pastFailures: z.array(z.string()),
    valuesAccumulated: z.array(z.string()),
  }),
};

export const GoalCardSchema = z.object({
  flowSummary: z.string(),
  visionRaw: z.string(),
  // ... 成果物の項目 ...
  ...ProfileFields,        // ← 末尾に置く
});
```

**項目を末尾に置いたのは意図的**です。構造化出力はスキーマの順に生成されるので、先に成果物を書かせ、対話全体を通した理解ができあがった状態でプロフィールを書かせたい。先頭に置くと、まだ何も整理していない状態で「持ち越す情報」を選ばせることになります。

呼び出し側は分解して返すので、**クライアントの契約は変わりません**。

```ts
const { profile, ...card } = cardRes.parsed_output;
return Response.json({ card, profile: profile ?? EMPTY_PROFILE, usage: usageOf(cardRes, STRUCTURE_MODEL) });
```

### 実測

```
入力 4518  出力 2943  37.2秒
profile: {
  lifePatterns: ["平日は本業で消耗していて、帰宅後は机に向かう気力が残っていないことが多い", ...],
  pastFailures: ["三日坊主になりがちで、去年も同じ理由で一度やめた"],
  valuesAccumulated: ["人に使われている実感"]
}
OK: 1回の呼び出しで成果物と profile を同時に取れた（4項目）
```

品質も落ちていません。むしろ、対話全体を1回で読んだうえで書いているぶん、切り貼りになりにくいはずです。

### トレードオフ

正直に書いておきます。**カードの生成に失敗すると、プロフィールも巻き添えで失われます**。以前は独立していたので片方だけ生きる可能性がありました。
ただし失敗時はどのみちエラー画面を出して再試行させるので、実害は小さいと判断しました。

## 7. いまのコスト構造（実測ベースの概算）

1セッション（small、14ターン）あたり:

| 内訳 | トークン | 単価 | 概算 |
|---|---|---|---|
| 対話 入力 | 約 31,000 | haiku $1/M | 4.8 円 |
| 対話 出力 | 約 1,100 | haiku $5/M | 0.9 円 |
| 整理 入力 | 4,518（実測） | sonnet $3/M | 2.1 円 |
| **整理 出力** | **2,943（実測）** | **sonnet $15/M** | **6.8 円** |
| 合計 | | | **約 15 円** |

（施策4で消えたぶん: 約 1.3 円）

**注目すべきは、整理の出力だけで全体の約45%**という点です。
`visionOptions` `specificOptions` `measurableOptions` `rationaleOptions` … と、ほぼ全項目に3案を出させているためです。`max_tokens: 16000` が必要になっているのはその結果です。

出力トークンは入力の5倍単価です。**次に効くのは、間違いなくここ**。

- 本命1案だけ生成し、「他の案を見る」を押された項目だけ追加生成する
- 押される項目は一部のはずなので、出力トークンは半分以下になる見込み
- 「決めるのは本人」という設計思想とも矛盾しない（3案を横に並べるより、1項目ずつ選ばせるほうが選択負荷は低い）

対話側で残っている手は、キャッシュではなく**履歴の圧縮**です。`ChatMessage` が `phase` を持っているので、完了フェーズのアシスタント発言だけを落とせば履歴が約半分になります（コーチの問いは、ユーザーの答えから復元できる）。決定論的なルールなので、プレフィクスは安定したままです。

## 9. 持ち帰り

1. **キャッシュは失敗しても黙っている。** 効いている証拠（`cache_read_input_tokens`）を見るまで、効いていると思い込める
2. **計測が先、最適化が後。** 順番を逆にしたので、効かない施策に手を入れてから気づいた
3. **入力トークンは合計で見ない。** 定価・読み出し・書き込みで単価が10倍以上違う
4. **文字数からトークン数を推定しない。** `wc -m` のバイト数で3倍ずれた。実測すれば1回で分かる
5. **出力トークンは入力の5倍。** 「何案出させるか」はコスト設計そのもの
