### 指摘1（重度：高）同期エラーの帯が、出たら消えず・閉じたら戻らない

**ファイル**

- `src/lib/supabase/sync.ts:146`（`noteFailure`）
- `src/components/SyncStalledBar.tsx:54`（表示条件）、`:89`（閉じるボタン）

**発生条件**

`lastSyncError` に `null` を代入している箇所が**コード全体に一つも無い**。
確認した代入箇所は `noteFailure` 内の1つだけである。

```
$ grep -rn "lastSyncError\s*=" src/
src/lib/supabase/sync.ts:146:  lastSyncError = {
src/lib/supabase/sync.ts:396:      if (lastSyncError === before) pushed.push(key);
```

`SyncStalledBar` の表示条件は `error !== null` を含むため、
**一度でも同期が失敗すると、その後どれだけ成功しても帯が出続ける**。
起こる場面は3つある。

1. 一時的な通信断で `pushKey` が1回失敗する（電車の中、Wi-Fi切り替えなど）
2. `healIfDanglingReference()` による自己修復（`e9132e8`）が**成功した直後**。
   `noteFailure` を呼んでから `backfillAll()` を走らせる順序なので、
   修復が完全に成功しても `lastSyncError` は残る
3. `backfillAll` の途中で1キーだけ失敗した場合

**利用者への影響**

「クラウドへの保存が止まっています。いまの入力は、この端末にだけ残っています。」
という帯が、**実際には保存できているのに出続ける**。竜一さんはこの文言を見て
別端末での確認や再ログインを試すことになる。

さらに悪いのは、それを鬱陶しく思って「閉じる」を押したときである。
`dismissed` は `useState(false)` のまま**二度と false に戻らず**、
`onSyncError` が新しいエラーを流し込んでも表示は復活しない。
リロードするまで、**本物の失敗が完全に無言になる**。

これは前日の作業（`651ab9e`）が直そうとした
「保存が失敗し続けているのに、本人は気づかないまま入力を続ける」
という壊れ方そのものである。

**修正候補**

- `pushKey` の各 case が正常終了したときと、`backfillAll` が `ok: true` で終わったときに
  `lastSyncError = null` を代入し、`errorListeners` へ `null` を配る
  （購読側は既に `null` を受け取れる型になっている）
- `healIfDanglingReference` は、修復が成功したらエラーを取り下げる
  （`noteFailure` を呼ぶ前に判定して、修復成功時は記録しない、でもよい）
- `SyncStalledBar` の `dismissed` は「そのエラー」に紐づける。
  `useEffect` で `error?.at` が変わったら `setDismissed(false)` に戻す

**確認方法**

1. ログイン状態で `/plan` を開き、DevTools の Network を Offline にして枠を1つ作る
   → 帯が出る（ここまでは意図どおり）
2. Offline を解除し、枠をもう1つ作る → Supabase には保存されるが**帯は消えない**
3. 帯の「閉じる」を押す → 再度 Offline にして枠を作っても**帯は出ない**

### 指摘2（重度：高）カレンダーを再連携すると、時間割の枠が削除される

**ファイル**

- `src/app/api/calendar/callback/route.ts:38`（毎回 `createCalendar`）
- `src/lib/calendar/engine.ts:163`（`googleEventId` が見つからない → `cancelled`）
- `src/lib/calendar/decide.ts:63`（`cancelled` かつ書き込み無し → `deleteBox`）
- `src/components/CalendarSyncBoot.tsx:101`（`deleteTimeBox` の実行）

**発生条件**

連携のコールバックは、毎回**新しい専用カレンダーを作る**。

```ts
// callback/route.ts:36-39
const { refreshToken } = await exchangeCode(code, ...);
const accessToken = await refreshAccessToken(refreshToken);
const calendarId = await createCalendar(accessToken, CALENDAR_NAME); // ← 常に新規
const ok = await saveLink({ refreshToken, calendarId });
```

一方、時間割の枠が持つ `googleEventId` を消す処理は**どこにも無い**
（`grep -rn googleEventId src/` で確認。書き込むのは `CalendarSyncBoot` と mapper だけ）。

そのため「連携を解除する → もう一度連携する」あるいは
Googleの同意画面をもう一度通っただけで、次の同期はこうなる。

1. `listEvents` は**空の新しいカレンダー**を見に行き、0件を返す
2. 各枠は `b.googleEventId` を持つのに `byId` に無い
   → `eventStateOf` が `"cancelled"` を返す（`engine.ts:163`）
3. メタ認知・振り返りが未記入の枠は `decideCalendarAction` が `"deleteBox"` を返す
4. `CalendarSyncBoot.tsx:101` の `deleteTimeBox(id)` が実行される

**利用者への影響**

`DELETE_BRAKE` は5件なので、**削除対象が5件以下なら何の確認も無く消える**。
6件以上なら「N件を削除しようとしています」の帯が出るが、
再連携の直後にこれを見た本人が「カレンダー側の予定を消すのだな」と読み違えて
「確認して削除する」を押すと、**期間内の枠がまとめて消える**。
消えるのはアプリ側の枠（title/start/end に加え color・cardId・habitId も一緒に）で、
localStorage からも Supabase からも消える。

なお `-7日〜+60日` の窓の外へGoogleカレンダー上で予定をドラッグした場合も、
同じ経路で枠が削除される（こちらは頻度が低いので併記にとどめる）。

**修正候補**

いちばん筋がよいのは、**「見つからない＝削除された」という推論をやめる**ことである。
`listEvents` は `showDeleted: true` と `singleEvents: true` を付けているので、
本当に削除された予定は `status: "cancelled"` として結果に含まれる。
つまり `engine.ts:163` の推論は本来不要で、これを落とすだけで再連携事故は消える
（見つからない枠は `"missing"` → `createEvent` となり、新カレンダーに作り直される）。

推論を残すなら、次のどちらかを併用する。

- `TimeBox` に `googleCalendarId` を持たせ、現在の `link.calendarId` と一致するときだけ
  `cancelled` と推論する
- `/api/calendar/status` が `calendarId` を返し、`CalendarSyncBoot` が
  前回と違えば全枠の `googleEventId` を `null` に落としてから同期する

**確認方法**

`tests/calendar-engine.test.mjs` に次のケースを足せば、実通信なしで再現できる。

- `boxes` に `googleEventId: "old-event-1"` を持つ枠を3件、`hasNotes: false` で渡す
- `listEvents` のモックが `{ ok: true, events: [] }` を返す（＝新しい空のカレンダー）
- 期待：現状は `result.deletes.length === 3`。修正後は `result.upserts` に
  新しい `googleEventId` が3件入り、`deletes` は空

### 指摘3（重度：中）24:00 に終わる枠が、カレンダーと噛み合わない

**ファイル**

- `src/lib/calendar/engine.ts:58`（`toRfc3339`）、`:81`（`fromRfc3339`）、`:294`（`updateBox`）
- `src/lib/timebox.ts:184`（`slotAt`）、`src/lib/api-schema.ts:159`（時刻の正規表現）

**発生条件**

このアプリでは `end: "24:00"` が正規の値である。`toTime(1440)` がこれを作り、
`toMinutes` はわざわざ 1440 として受けるようにしてある（`timebox.ts:26-30` のコメント参照）。
一日の最後のマス（23:30–24:00）をタップすれば `slotAt(1439)` 経由で普通に作られる。

`api-schema.ts:159` の `/^\d{2}:\d{2}$/` は `"24:00"` を通す。
その値がそのまま `toRfc3339` に渡ると、こうなる。

```ts
toRfc3339("2026-09-07", "24:00") // → "2026-09-07T24:00:00+09:00"
```

RFC3339 は `time-hour = 2DIGIT ; 00-23` と定めており、**24時は表現できない**。
どちらに転んでも壊れる。

- **Googleが400で弾く場合**（RFC3339の仕様からの推論。実測はしていない）
  `insertEvent` / `patchEvent` が throw し、`engine.ts:307` の catch で `failed++`。
  `link.lastError` に「1件の同期に失敗しました」が残り、**同期のたびに永久に再試行する**。
  設定画面には毎回エラーが出続ける。
- **Googleが受理して翌日0時に正規化する場合**（こちらは経路を実行して確認済み）
  JS の `Date` も同じく翌日へ繰り上げる。

  ```
  $ node -e 'console.log(new Date("2026-09-07T24:00:00+09:00").toString())'
  Tue Sep 08 2026 00:00:00 GMT+0900 (日本標準時)
  ```

  すると `fromRfc3339` が返す `evEnd.date` は翌日になり、`engine.ts:262` の
  `evEnd?.date === b.date` が**永久に false** になる。`contentEqual` が成立しないので、
  同期のたびに `updateEvent` か `updateBox` が走り続ける。
  `updateBox`（`engine.ts:294-302`）に倒れた場合は枠に `end: "00:00"` が書き込まれ、
  23:30–00:00 という**長さ0分の枠**になる。これは `timebox.ts:28` のコメントが
  「グリッド上で最小の高さに潰れる」として過去に一度直した壊れ方そのものである。

**利用者への影響**

夜の最後の枠だけがカレンダーに出ない、または同期のたびに枠が潰れる。
毎晩使う時間帯なので、遭遇頻度は低くない。

**修正候補**

`toRfc3339` で 24:00 を「翌日の 00:00」へ正規化し、`fromRfc3339` から戻すときは
`start` と同じ日で終わる枠なら `24:00` へ畳み直す。

```ts
export function toRfc3339(date: string, time: string): string {
  if (time === "24:00") return `${nextDay(date)}T00:00:00+09:00`;
  return `${date}T${time}:00+09:00`;
}
```

（日付の加算は `src/lib/date.ts` のヘルパーを通すこと。素朴な `+ 86_400_000` は使わない。）

`engine.ts:336` の第2ループには既に `if (s.date !== en.date) continue;` という
日跨ぎガードがあるが、第1ループの `updateBox` 側には無い。ここにも同じ配慮が要る。

**確認方法**

`tests/calendar-engine.test.mjs` に `{ start: "23:30", end: "24:00" }` の枠を1件渡し、
`insertEvent` のモックが受け取った `endIso` を検証する。
現状は `"...T24:00:00+09:00"` が渡ることが確認できるはず。

- テスト・型チェック・ビルドがすべて成功する（実行）

**未検証（実通信が要るもの）**

- Google Calendar API が `24:00:00` を400で弾くかどうか。RFC3339 の仕様上そうなるはずだが、
  実際のレスポンスは確認していない。**弾かれても受理されても壊れる**ので、
  指摘3の結論はどちらに転んでも変わらない
- `/api/mcp` が Supabase クライアントに MCP の JWT をそのまま渡している
  （`route.ts:22-25`）。発行者が Supabase でない場合 PostgREST が検証に失敗するはずで、
  その場合はツールが動かない。ただし**失敗する側に倒れる**ので危険は無い。
  環境変数が無いと動かせないため未検証、指摘には含めなかった
