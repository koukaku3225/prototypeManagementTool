# 週間・月間の中間目標機能の調査

日付：2026-09-13
種別：調査
状態：完了（設計案の提示まで。実装はしていない）

## 結論

大目標（BigStory）と実行（TimeBox・Habit）の間に「週または月の単位で、期間をユーザーが選べる中間目標（Milestone）」を挟む機能は、行動科学の裏付け（目標分解による自己効力感の向上）があり、追加する価値があると判断できる。

ただし設計を誤ると「誰も更新しなくなる形骸化した階層」になりやすいことも、企業向けOKRツールの失敗事例から確認できた。押さえるべき要点は次の3つ。

1. **更新の手間を専用画面の儀式にしない。** 目標一覧・タイムボックス操作の「ついで」に見える／更新できる場所に置く。
2. **期間（週/月）は目標作成時に一度だけ選ばせ、デフォルトを提示する。** 毎回選ばせると意思決定疲れを招く。
3. **タイムボックスの実行意図（なぜ重要か・障害・対策）と役割を分ける。** 中間目標は「今週・今月、何をなぜ」という大枠に留め、既存機能と粒度を重複させない。

UIの置き場所は、既存の `/goals` 画面の目標カード内（習慣・次の予定と並ぶ位置）が最有力。対話フェーズには追加せず、手動UI（フォーム・+ボタン）で完結させるのが妥当。

## 依頼と背景

現在のアプリは「大きな物語（BigStory、1〜10年）」→「Small目標（GoalCard、最大3件）」→「習慣・時間割（Habit・TimeBox、日次）」の2段階構造で、その間に中期スパンの目標が存在しない。竜一さんから「大目標をクリアするためのテーマをさらに細分化した、週〜月単位の中間目標を追加したい。期間はユーザーが設定できるようにしたい」という要望があり、実装前に以下を調査するよう依頼された。

- どんな仕様がありうるか
- 現状のアプリのどこにどう追加するのが自然か
- どのようなUI・デザインならユーザーが使い続けるか、逆に使われなくなるか
- どのような設計にすると目標達成しやすくなるか

「コンテキストを消費したくない調査項目はサブエージェントに任せる」という指示があったため、以下の3系統を並列のサブエージェントに調査させ、その結果を統合した。

## 調査結果

### 1. 現状のコードベースへの統合方法（Explore agentによる調査）

**現在のデータ階層**（正規化されたフラット配列、埋め込み禁止という既存方針を踏襲）:

```
BigStory（gc.bigstory, 1件）
  └─ GoalCard（gc.cards[], bigStoryId で紐付け・null可）  最大3 active
       ├─ Habit（gc.habits[], cardId必須）
       │    └─ HabitLog（habitId+date の複合キー）
       └─ TimeBox（gc.timeboxes[], cardId任意, habitId任意）
```

`GoalCard` には `smart.deadline`（単一日付）はあるが期間概念がなく、「週〜月の期間を持つ中間目標」に対応する型は現状どこにも存在しない。

**追加すべき型（案）**: `src/types/goal.ts` に `Milestone` を新設。

```ts
interface Milestone {
  id: string;
  cardId: string;              // GoalCard.id 必須（Habit.cardIdと同じ思想）
  title: string;
  period: { kind: "week" | "month"; start: string; end: string };
  status: "active" | "done" | "abandoned";
  order: number;
  createdAt: string;
  updatedAt: string;
}
```

`GoalCard` に `milestoneIds` のような配列を持たせるのは禁止パターン（AGENTS.mdの「GoalCardに日々ログを埋め込まない」原則、`upsertCard` がカード全体を置換する設計と衝突する）。必ず別キー・別配列にする。

**新設が必要なファイル・関数**:
- `src/lib/storage-keys.ts`: `KEY.milestones = "gc.milestones"`
- `src/lib/storage.ts`: `loadMilestones()` / `milestonesOfCard(cardId)` / `upsertMilestone(m)` / `deleteMilestone(id)` / `deleteMilestonesOfCard(cardId)`（`deleteCard` 内で他の `deleteXxxOfCard` と並べて呼ぶ）
- `SNAPSHOT_TARGETS` に `KEY.milestones` を追加（既存ルール、忘れるとスナップショット復元で取り残される）
- `src/lib/milestone.ts`: 進捗率計算などの純粋関数群（`habit.ts`/`timebox.ts` と同じパターン）
- Supabase側: `mappers.ts` に `milestoneToRow`/`milestoneFromRow`、`sync.ts` の `pushKey()` の switch文・`pullAll()`・テーブル一覧に追加、新規テーブル `milestones` のマイグレーション

**UI統合先**: 新規タブは不要（BottomNav.tsx の「頻度の桁が違うものを同列に置かない」思想に反する）。最有力は `/goals` 画面のGoalRow内、既存の「習慣」「次の予定」表示の直前に「中間目標」セクションを追加する案。この画面は既に `habitsOfCard`/`timeBoxesOfCard` というカードごと集計のパターンを持っており、`milestonesOfCard` を同じ形で差し込める。作成・編集操作は目標詳細画面（`/goal/[id]`）に置くのが自然。

**対話フェーズへの組み込みは非推奨**: `PHASE_ORDER`/`SMALL_FLOW` は過去に「いつまで続くか分からない」というフィードバックを受けて5フェーズ39ターンから3ステップへ短縮された経緯がある（AGENTS.md記載）。対話ターンを増やす方向の変更はこの反省に逆行する。中間目標は「週〜月ごとに随時追加・更新する」性質上、GoalCard確定時の一回性の対話とはライフサイクルが異なるため、手動UI（+ボタン、フォーム）で完結させるのが妥当。

**進捗可視化に転用できる既存パターン**: `Heatmap.tsx`（7列グリッドの色分け、週単位に変換可）、`WeekShareBar.tsx`（時間配分バー、「未着手」を責めない文言で見せる設計）、`HabitCheck.tsx`（streak表示）。全体に「達成率を責める文言にしない」という一貫したUIポリシーがあり、中間目標もこれに従うべき。

### 2. 週次/月次UIの事例（Web調査）

- **Sunsama**: 週次オブジェクティブを日次プランニングの中に埋め込み、タスク作成時に参照させる。専用の更新儀式を要求しない設計。
- **Full Focus Planner**: 四半期ゴール→週次「Big 3」→日次Big 3の3階層。週次プレビューで前週を振り返り、今週の3つをゴールから逆算して決める。
- **企業向けOKR（Weekdone/Perdoo/15Five）**: 週次チェックインを行うチームはOKR達成率43%、隔週/月次は27%、リズムなしは10%未満というベンチマークがある一方、これは「他者への説明責任がある組織文脈」のデータであり、個人利用にそのまま適用できるとは限らない。
- **失敗パターン**: 進捗更新に複数ステップを要する「摩擦」、記録場所の分断（スプレッドシート・Slack・頭の中）、「2週間更新なしはすでに形骸化のサイン」という経験則。
- **進捗の見せ方**: 進捗バー/％は終点が明確な成果目標向き、ストリークは二値の習慣向き、ヒートマップは習慣・健康系と相性が良い。1つの形式を全ゴールに一律適用するとミスマッチが起きる。

### 3. 行動科学の知見（Web調査）

- **目標分解の効果**: Locke & Lathamの目標設定理論では、遠位目標（distal goal）のみでは複雑・長期的な課題に不十分で、近位目標（proximal sub-goal）への分解が自己効力感・粘り強さ・パフォーマンスを高める。近位・遠位を併用した群が遠位のみの群より高い成果を出すという知見もあり、今回の「ビジョン→中間目標→実行」という3階層化を直接支持する。
- **実行意図との役割分担**: Gollwitzerのif-then計画（実行意図）は目標達成率を中〜大の効果量で押し上げるが、計画が詳細・硬直的になりすぎると不測の事態への適応力を損なう。中間目標は「今週・今月、何をなぜ」という大枠に留め、詳細な障害・対策は既存のタイムボックス機能に残す役割分担が、冗長化と硬直化の両方を避ける。
- **モニタリング頻度**: 進捗モニタリングは目標達成を促進する（Harkinらのメタ分析）が、頻度が高すぎると「見つめる鍋は煮えない」効果や燃え尽きを招き、低すぎると軌道修正が手遅れになる。「数秒で終わる日次確認＋数分の週次レビュー」の二層構造が継続率を保ちやすい。
- **柔軟性と挫折**: 目標への柔軟性の欠如（オール・オア・ナッシング思考）は少しの停滞で目標全体を放棄させることが複数の研究で示されている。柔軟に目標を再調整できる設計（goal reengagement）の方がドロップアウト率が低く、生活満足度とも正の関連がある。
- **自己決定理論（SDT）との関連**: 自律性・有能感・関係性が満たされるとき内発的動機づけが強まる。「なぜやっているか」を定期的に、かつ本人の選択として再確認させる設計は、外的な義務としてではなくモチベーション維持に寄与する。

## 仕組みの説明

今回追加するとすれば、次のような操作の流れになる（設計案。未実装）。

1. 目標詳細画面（`/goal/[id]`）で「中間目標を追加」を押す。
2. タイトルと期間（週／月のどちらか、目標の性質に応じたデフォルト値を提示）を入力する。
3. 作成した中間目標は、`/goals` の目標カード上に「習慣」「次の予定」と並ぶセクションとして表示される。開かなくても進捗の概要が見える。
4. 進捗は目標の種類に応じて、進捗バー（成果目標）かヒートマップ/ストリーク（頻度ベースの目標）で表示する。
5. 期間が終わる、または大きく停滞したときは、責めない文言で「続ける／内容を見直す／今回は終わりにする」を選べるようにし、オール・オア・ナッシング思考による離脱を防ぐ。
6. 対話（AIコーチング）には組み込まず、既存の対話フローとは独立した機能として動く。

## 確認したこと

- 現在の型定義・storage.ts・主要画面（goals/plan/BottomNav）のコードを実際に読み、既存の実装パターンと矛盾しない追加方法を確認した。
- 「GoalCardに配列を埋め込まない」というAGENTS.mdの既存原則に、案C（GoalCardへのmilestoneIds直接埋め込み）が抵触することを確認し、除外した。
- 対話フェーズのターン数に関する過去の反省（AGENTS.md記載）を踏まえ、対話への追加を推奨しない判断の根拠とした。
- 行動科学の主張は、複数の一次研究・メタ分析（Locke & Latham、Gollwitzer、Harkinら、自己決定理論）を情報源として確認した。企業OKRのベンチマーク数値は業界レポート由来であり、個人利用への一般化には注意書きを添えた。

**実装・実機での動作確認はしていない**（今回は調査・設計案の提示までの依頼のため）。

## 残っていること

- 型定義・UI配置・進捗可視化のどの案を採用するか、竜一さん自身の判断が必要（AIは選択肢を狭めない、という方針にも合致する）。
- 実装する場合は、まず型とstorage.tsの関数を追加し、次に`/goals`画面への表示、最後にSupabase同期という順で進めるのが既存の開発パターンに沿う。
- 「期間終了時の責めない文言」「進捗可視化の切り替え基準（成果目標かどうかの判定方法）」は、具体的な文言・UIモックの検討がまだ残っている。
- HTML報告書を別途 Artifact として公開済み（竜一さんへの提示用）。
