# アプリのセキュリティレビュー

日付：2026-09-14  
種別：調査  
状態：追加のオフライン再現試験まで完了。本番設定・DB権限の確認は残件。

## 結論

優先すべき問題は、バックアップAPIの無認証アクセス、アカウント間のデータ分離、復元時のデータ破壊である。追加調査で7件の問題を整理し、合計13件の指摘と2件の補足を記載した。10件はコードまたは隔離試験で問題の仕組みを確認、3件（4〜6）は本番設定・DB権限次第の指摘である。この件数は本番で成功した攻撃の数ではない。

閲覧用の [HTMLレポート](2026-09-14-security-review.html) と、架空データだけで動く [再現スクリプト](security-review-evidence.cjs) を併せて保存した。

「本番で漏洩している」と確認したものではない。以下では実行確認、コード上の問題、設定依存のリスクを区別する。アプリのコード・設定・実データは変更していない。

## 依頼と背景

プロのセキュリティエンジニアの観点から脆弱性を洗い出す依頼。対象はNext.jsのAPI、認証、localStorageとSupabase同期、Google Calendar OAuth、MCP、入力検証、セキュリティヘッダ。対話・価値観・挫折・予定を扱うため、機密性とデータの完全性、従量課金APIの濫用を重視した。

## 調査結果

### 1. 高：バックアップAPIが認証なしで全データを読み書きする【隔離環境で再現】

根拠：[バックアップAPI](../../src/app/api/local-backup/route.ts) の35行以降、103行以降。

- POSTは認証・Origin確認・開発環境確認をせず、全利用者共通の `.local-backups/latest.json` を更新する。
- GETも認証なしで最新バックアップ全体を返す。`REQUIRE_AUTH=true` はこのAPIに効かない。
- 30世代を超えたファイルを自動削除するため、連続した偽バックアップで正常な世代を追い出せる設計でもある。削除攻撃自体は実施していない。
- [LocalBackupBoot](../../src/components/LocalBackupBoot.tsx) のlocalhost判定はブラウザからの自動送信を止めるだけで、API直アクセスを制限しない。

悪用条件は、攻撃者がサーバーへ到達でき、バックアップファイルをサーバーが読み書きできること。LANに公開された開発サーバーやディスク永続型のホスティングで特に問題となる。`next dev` の既定hostnameは `0.0.0.0` だが、実際の外部到達性はファイアウォール等に依存する。[Next.js公式CLI](https://nextjs.org/docs/app/api-reference/cli/next)

Vercelで最新バックアップが存在・読み取り可能とは確認していない。書き込み不可の環境と、情報漏洩が成立する環境は区別が必要。

**確認結果：** 一時ディレクトリへ作業先を切り替え、実際のルート関数を呼んだ。`NODE_ENV=production`、`REQUIRE_AUTH=true`、資格情報なしでPOST=200、GET=200、架空データの一致を確認。HTTPサーバー・middlewareを含めた侵入試験ではない。元のバックアップには触れていない。

**推奨：** 本番ではサーバー側で404。ローカル機能は明示的な有効化、loopbackへのバインド、アクセス用の秘密値、厳密なOrigin検証を組み合わせる。Hostヘッダだけを認証に使わない。バックアップの所有者も区別する。

### 2. 高：ログアウトしても個人データが残り、別アカウントの同期対象になる【コード確認・判断関数を再現】

根拠：[設定画面](../../src/app/settings/page.tsx) 207行、[同期処理](../../src/lib/supabase/sync.ts) 745〜790行・858行以降、[同期判断](../../src/lib/supabase/sync-decision.ts)、[目標画面](../../src/app/goals/page.tsx) 85行。

ログアウトは `auth.signOut()`、同期側は `disablePush()` を呼ぶだけで、ブラウザ内の個人データを隔離・ロックしない。画面は共通のlocalStorageから読み続ける。共有ブラウザを次に使う人は、ログインせず前の人の目標等を閲覧できる構造。

さらに、Aのデータが残るブラウザでクラウドが空のBへログインすると、「未同期・ローカルあり・クラウドなし」は `push` となり、`backfillAll()` が走る。所有者の引き継ぎ同意がない。[マッパー](../../src/lib/supabase/mappers.ts) は現在のuserIdを付けて送るので、プロフィール等がBの保存対象になる。IDが衝突する行はDB制約で拒否される可能性があり、全テーブルのコピー成功を断定しない。

**確認結果：** 実際の `decideSyncDirection({alreadySynced:false, localHasContent:true, cloudHasContent:false})` が `push` を返した。本番でA/Bを切り替える試験は未実施。

**推奨：** 保存領域とバックアップをユーザー別に分け、ログアウト時に表示中データとメモリも解除する。既存のゲストデータは所有者を確認して明示的に移行する。消失事故の経緯があるため、単純な全消去を修正案にしない。

### 3. 中：JSON必須チェックをすり抜け、クロスサイト送信の防御が崩れる【パーサーで再現】

根拠：[parseBody](../../src/lib/api-schema.ts) 203行、[バックアップAPI](../../src/app/api/local-backup/route.ts) 37行。

Content-Typeを `includes("application/json")` で判定しているため、`text/plain; note=application/json` でもJSONとして受け付ける。実際のparseBodyに空の架空JSONを渡して `ok:true` を確認した。

ブラウザのCORS判定はパラメータを除いたMIMEタイプを見るため、このヘッダはプリフライトを必須にする防壁にならない。攻撃元が応答を読めなくても、POSTによる副作用は別問題。[MDN CORS仕様説明](https://developer.mozilla.org/en-US/docs/Glossary/CORS-safelisted_request_header)

認証なしAI APIなら他人のブラウザ経由で呼び出しを誘発できる条件となる。バックアップ汚染にもつながり得る。ただし認証必須のAPIではSameSite Cookie等、localhostではブラウザのローカルネットワーク保護等が別途関係する。認証付きカレンダーへのクロスサイト攻撃成功までは確認していない。

**推奨：** MIMEタイプを分解して `application/json` と厳密比較する。Cookie認証による変更APIはOrigin/CSRF防御も持つ。disconnect APIも本文なしPOSTを受けるため同じ方針で保護する。

### 4. 高（条件付き）：認証・レート制限が未設定や障害時に開き、AI APIの課金濫用につながる【コード確認】

根拠：[require-auth](../../src/lib/require-auth.ts) 36行、[rate-limit](../../src/lib/rate-limit.ts) 100行・126行、[structure API](../../src/app/api/structure/route.ts)。

`REQUIRE_AUTH` が厳密に `true` でなければ匿名利用可能。Upstash未設定時や通信・認証エラー時は制限なしで通過する。structureでは最大16,000出力トークンを要求できる。公開環境でこれらの条件が重なると、第三者が契約者負担で生成を繰り返せる。ログイン必須でも、利用制限自体が失効するリスクは残る。

これは意図した可用性優先の実装だが、費用の安全性とトレードオフになっている。本番環境変数とAnthropic側の支出上限は未確認。課金が発生する実行はしていない。

**推奨：** 本番起動時に必須設定を検証する。制限サービス障害時は無制限ではなく保守的な代替上限または一時拒否にする。利用者単位に加えて全体予算と同時実行数を制限し、ゲスト利用が必要なら専用の小さい枠を用意する。

### 5. 高（条件付き）：外部AIの「読み取り専用・対話全文非公開」がDB直アクセスでは保証されない【本番RLS監査が必要】

根拠：[同意画面](../../src/app/oauth/consent/Consent.tsx)、[MCPルート](../../src/app/api/mcp/route.ts) 19〜24行、[MCP実装報告](2026-09-06-mcp-implementation.md)。

MCPは受け取ったSupabase OAuthトークンをDBへ転送して使う。MCPのツールを読み取り専用・列限定にしても、連携先が同じトークンでSupabase REST APIを直接呼べる場合、制約はDB側のRLSと列権限に依存する。

Supabase公式にも、OAuthトークンには既存RLSが適用され、`client_id` によるアクセス制限が必要と記載されている。本人IDだけのポリシーでは、通常ログインと外部AIを区別できない。[Supabase Token Security and RLS](https://supabase.com/docs/guides/auth/oauth-server/token-security)

既存報告にも「実DBのRLS・列権限の監査と、MCPトークンによる直接書き込み拒否試験」が未完として残る。今回も実DB・MCPの有効状態を確認できていないため、現存する本番の権限逸脱とは断定しない。

**推奨：** 有効化前に、外部AIのトークンによる対話・プロフィール・Calendarトークンの直接SELECT拒否と、INSERT/UPDATE/DELETE拒否を検証する。client_idを考慮したRLSに加え、限定ビュー・列権限・API境界を設計する。OAuthの同意文言だけではDB権限は制限されない。

### 6. 中〜高（条件付き）：Googleの長期トークンを通常のユーザー資格情報で読める設計【コード・設計SQL確認】

根拠：[calendar/link](../../src/lib/calendar/link.ts) 43〜62行・84行、[Supabaseサーバークライアント](../../src/lib/supabase/server.ts)、[設計SQL](../superpowers/plans/2026-09-05-google-calendar-sync.md) 548〜563行。

サーバー関数は特別なサーバー専用DB資格情報を使わず、Cookie上のユーザーセッションと公開キーで `google_calendar_links.select("*")` を行い、平文refresh_tokenを得る。設計SQLも本人行の全操作を許す。「アプリのAPIでトークンを返さない」ことと「ブラウザ資格情報でDBから直接読めない」ことは異なる。

本番でこの設計どおりに動作し、DB側に別の制約がなければ、同じセッションを得た攻撃者やXSSが長期トークンを抽出し得る。Google OAuthクライアントシークレットもトークン交換に使うため、refresh_token単体で直ちに全予定が読めるとまでは断定しない。しかし秘密値をサーバー限定にする境界は成立していない。

**推奨：** トークンは一般ユーザー・OAuth連携クライアントから読めない専用領域へ置き、認証済みのサーバー処理だけで利用する。アプリ側暗号化やVaultも検討する。本番RLS・列権限の確認が必要。

### 7. 高：進行中の同期がアカウント切り替えをまたぎ、旧利用者の情報を復活・送信する【実関数＋DBモックで再現】

根拠：[sync.ts](../../src/lib/supabase/sync.ts) 552〜588行、609〜677行。

指摘2は保存領域の共有という静的な問題。こちらは非同期処理の寿命と所有者が結び付いていない別の問題で、ログアウト時に画面を消す対策だけでは残る。

- `pullAll()` は開始時にuserIdを保持するが、DBの応答を待った後、現在のユーザーと再比較せず `restoreState()` を呼ぶ。上位呼び出しの比較は復元の後なので遅い。
- `backfillAll()` はAのスナップショットを一度取得した後、キーごとに `pushKey()` を呼ぶ。各 `pushKey()` がその時点のcurrentUserIdを取り直すため、途中でBになれば残りのAデータへBの所有者IDを付ける。

**再現：** AのpullをDBモックで待機させ、ログアウトしてメモリ上の保存領域を空にし、その後DB応答を返した。同期状態がoffでもAのプロフィールが復元された。別の試験では、Aのbackfill中にBへ切り替え、Aのプロフィールが `user_id=synthetic-B` でDBモックに送られた。

**影響・条件：** 同一ブラウザで切り替えと通信待ちが重なる必要がある。Bのクラウドが空でなくても旧バッチは走り続ける。実DB上の書き込み成功はRLS・列・主キー等の制約にも依存する。本番アカウントでの再現はしていない。

**推奨：** 同期開始時のuserIdと世代番号を全処理へ渡し、各awaitの後・保存直前・次の送信前に照合する。アカウント変更でAbortControllerも中断する。データのユーザー別保存と併用する。

### 8. 高：正常なバックアップの復元でも、クラウドには削除だけを通知する【実ストレージ関数で再現】

根拠：[storage.ts](../../src/lib/storage.ts) 176〜184行、1029〜1055行、[設定画面](../../src/app/settings/page.tsx) 373行以降、[sync.ts](../../src/lib/supabase/sync.ts) のpushOne。

`restoreState()` は既存キーを `remove()` で消す。removeは同期フックへ `(key, null)` を送り、bigstoryやprofileの処理はDB削除を行う。一方、復元値は同期フックを通さず直接書き戻す。クラウド取り込みのpullAllは周囲で同期フックを止めているが、JSON読み込みとスナップショット復元では止めていない。

**再現：** 正常なプロフィールと現行版番号4を復元したところ、ローカルにはプロフィールが残るのに、同期フックへ渡ったprofile通知はnullの1件だけであった。復元後のプロフィールを再送する通知は0件。DBの実削除はしていないが、nullを受けたpushOneがDELETEを組み立てることをコードで確認した。

**影響・条件：** ログインして同期中に、本人が正常なJSONまたはスナップショットを復元するだけで発生する整合性の欠陥。次回backfillで戻る可能性はあるが、その間に別端末で取り込むと削除が伝播し得る。攻撃者の存在を要しないデータ完全性の問題として報告する。

**推奨：** 復元を一つの更新として扱い、同期を一時停止して検証・書き戻しを終え、成功した復元値だけを同期する。保留中・進行中の送信の扱いも統一する。

### 9. 中：細工した復元JSONがデータ消去や終了しない移行処理を起こす【隔離プロセスで再現】

根拠：[storage.ts](../../src/lib/storage.ts) 345〜347行・375〜383行・1086行以降。

importStateJsonは外側が「オブジェクトで全値が文字列」かだけを見る。アプリのバックアップか、内部データが正しいか、版番号が許可範囲かを検証せず、既存データの消去と移行を開始する。

**再現A：** 無関係な `{"unrelated":"not-an-app-backup"}` を渡すとtrueが返り、元のプロフィールが消えた。

**再現B：** `{"gc.schemaVersion":"-1e20"}` を渡すとrunMigrationsのwhileループが進まなくなる。JavaScriptのNumberは倍精度浮動小数点で、この値では `v + 1 === v` が成立する。C++で大きなdoubleへ1を足しても値が変わらない現象と同じである。隔離した子プロセスで移行開始を確認し、2.5秒で強制終了した。通信や本物の保存領域は使用していない。

**影響・条件：** 攻撃者が「復元用JSON」として渡したものを本人が読み込む、または指摘1のバックアップ改ざんを復元する必要がある。移行はブラウザのメイン処理上で動くためUIが応答しなくなり、破損した版番号が残れば再読込後も再発し得る。単なるJSON文法エラーではないので現在のcatchでは防げない。

**推奨：** 文書種別・許可キー・各内部JSON・版番号の安全な非負整数と範囲を消去前に検証する。移行は登録済みの有限ステップだけを実行し、復元失敗時は元データを残す。読み込み前に置換対象を表示する。

### 10. 中：無効なMCPトークンでも毎回認証サーバーへ鍵を取りに行く【ネットワークモックで再現】

根拠：[mcp/auth.ts](../../src/lib/mcp/auth.ts) 22〜32行、[MCP API](../../src/app/api/mcp/route.ts) 14〜18行。

authenticateMcpRequestは毎リクエスト `createRemoteJWKSet()` を生成する。joseの鍵キャッシュ・同時要求の統合・再取得間隔はそのインスタンスに属するので、要求をまたいで活用できない。アプリのレート制限は認証成功後にしか呼ばれない。

**再現：** 秘密鍵も有効な署名もない、構文上JWTの形をした文字列を3回送る処理を実行。3件とも拒否されたが、JWKS取得のfetchも3回呼ばれた。fetchは架空の公開鍵一覧を返すモックであり、本番へ負荷をかけていない。

**影響・条件：** MCPが有効・設定済みである場合、未認証の第三者が認証サーバーへの通信と関数実行時間を消費させられる。認証突破やSSRFを確認したものではない。外部WAF等の制限は別途あり得る。

**推奨：** issuer/JWKS URL単位の長寿命キャッシュと、認証前の小さい入口レート制限を併用する。JWKS URLはサーバー設定の許可先に固定する。

### 11. 中：MCPのバッチにより1回の制限枠で20回のツールを実行できる【実SDKで再現】

根拠：[api-schema.ts](../../src/lib/api-schema.ts) 51〜54行、[MCP API](../../src/app/api/mcp/route.ts) 18行、[rate-limit.ts](../../src/lib/rate-limit.ts)。

レート制限はHTTP要求ごとに1回だが、JSON-RPC本文は20件の配列を許している。インストール済みSDKのHTTP transportもこれを受け付け、各ツールを実行する。

**再現：** 実スキーマ・実MCPサーバー・実HTTP transportへ20件のget_goalsを一つの要求で渡し、HTTP 200とリポジトリモックの呼び出し20回を確認した。有効なMCP認証を通過した後の層を試験している。

**影響・条件：** 許可された連携クライアントの有効なトークンが必要。HTTP回数としての制限は動くが、DB・ツール実行量は20倍まで増え、5要求/分が最大100ツール/分、500要求/日が最大10,000ツール/日となる。盗んだトークンによる大量取得や連携先の暴走に対する制限が弱い。

**推奨：** バッチを拒否するか、バッチ内の実行件数をコストとして先に消費する。ツール実行数・並列数・DB取得量も制限する。

### 12. 中：カレンダー同期が小さい要求から大量のGoogle API操作へ増幅する【実エンジン＋外部モックで再現】

根拠：[calendar sync API](../../src/app/api/calendar/sync/route.ts)、[engine.ts](../../src/lib/calendar/engine.ts) 320〜359行、[google.ts](../../src/lib/calendar/google.ts) 222行・298行以降。

カレンダーAPIにはchat/MCPのような利用制限がなく、同期は一つの本文に最大500枠を許す。作成ループには件数予算・同時同期ロックがない。Google fetchや同期エンジンへ要求のAbortSignalも渡していない。一覧取得はページが続く限り読み込む。

**再現：** スキーマに合格する500件の架空枠を実runSyncへ渡し、insertEventモックが500回呼ばれた。Googleへの実書き込みは0回。実環境では通信速度・Googleの制限・VercelのmaxDurationにより全件完了前に止まる場合がある。

**影響・条件：** Google連携済み利用者の有効セッションが必要。悪意ある利用者または盗まれたセッションから、共有プロジェクトのクォータやサーバー実行時間を消費できる。利用者本人の予定表にも大量の作成が起き得る。Googleはプロジェクト単位と利用者単位のクォータを持つ。[Google Calendar API quotas](https://developers.google.com/calendar/api/guides/quota)

**推奨：** 利用者・プロジェクト単位の上限、同一利用者の同期排他、差分操作数の予算、AbortSignal、ページ取得上限を設ける。必要な大量同期は検証済みの小分けジョブにする。

### 13. 中：Google Calendar OAuthのstateがアプリ利用者に結び付いていない【コード確認】

根拠：[connect](../../src/app/api/calendar/connect/route.ts) 21〜30行、[callback](../../src/app/api/calendar/callback/route.ts) 23〜40行、[OAuth state](../../src/lib/calendar/oauth-state.ts)。

連携開始時のstate CookieはランダムUUIDだけで、開始したアプリ利用者IDを持たない。callbackはstate一致後、**callback時点**でCookieに入っている利用者へrefresh tokenを保存する。

同一ブラウザでAがGoogle Calendar連携を開始し、Googleの同意画面を開いたままログアウトしてBへログインし、その後コールバックへ戻ると、Aが選んだGoogleアカウントへの権限をBの行へ保存し得る。攻撃者が他人のブラウザ状態を変える必要があるため、通常は共有端末・アカウント切替・端末乗っ取り時に顕在化するアカウント紐付けの混乱である。stateの値そのものを推測・偽造できるとは報告していない。

**推奨：** stateをサーバー側の開始セッションとuserIdへ結び付け、callbackの利用者が開始時と異なる場合は交換・保存を中止する。stateは一度だけ使い、期限を維持する。

### 補足：多層防御の弱点

- **ボディサイズ制限が読み込み後：** [parseBody](../../src/lib/api-schema.ts) 207〜211行、バックアップ、MCPはいずれも全文をメモリへ読んだあと制限する。特に `raw.length` はバイト数ではない。実parseBodyで300,011バイトの架空JSONが200,000バイト上限を通ることを確認した（スキーマはこの境界だけを検証するための最小モック）。ホスティング側の上限がなければ巨大リクエストでメモリを圧迫できる。ストリーム読取中の実バイト制限が必要。大量データによる負荷試験は未実施。
- **CSPがinline scriptを許可：** [next.config.ts](../../next.config.ts) 32行の `unsafe-inline` はXSS発生時の防御を弱める。今回XSSの実経路は発見していないため、独立したXSS脆弱性とは数えない。nonce化を検討する。connect-srcを絞っても画面遷移などを含む全ての持ち出しを防げるわけではなく、「盗まれても外部へ送れない」とのコメントは保証が強すぎる。

## 仕組みの説明

このアプリのデータには三つの境界がある。ブラウザのlocalStorageは同じブラウザの利用者間で共有され、ログインとは独立している。バックアップはさらにサーバー全体で一つのファイルになる。Supabaseは直接アクセスできるDB APIなので、Next.js側だけで情報を隠してもDB権限が許せば取得できる。各境界で所有者・利用目的・許可された操作を独立して確認する必要がある。

C++のGUIと非同期I/Oに置き換えると、指摘7は古い所有者の処理完了通知が、新しい利用者へ切り替わったGUIや保存先へ適用される問題に近い。受付担当者が変わったあとで、前の人の荷物が新しい人のロッカーへ入る状態である。JavaScriptは同時に二つの命令を走らせなくても、awaitの間にアカウント変更イベントが入るため、この競合は起きる。DBのRLSは本人IDの認可を担当するが、クライアントがBのトークンとBのIDでAの内容を送る場合、「内容は元々Aのもの」という来歴までは自動で判別しない。
