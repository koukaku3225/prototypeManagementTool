## 直したもの

### 1. 繋ぎ直しのあと、時間割の枠が時間差で消える（重度：高）

**何が起きていたか**

別のカレンダーへ繋ぎ直すと、新しいカレンダーには古い予定IDが一つも無い。
同期エンジンはそれを「カレンダー側で削除された」と読むので、
放っておくと時間割が消える。これを防ぐために古いIDを落とす処理は入っていた。

ところが**落としていたのは「サーバーへ送る配列」の中だけ**で、
localStorage 本体はそのままだった。送信は日付で絞ってあるので、次の2つが残る。

1. **+60日より先の枠**（サーバーの処理窓の外なので作り直されない）
2. **作り直しに失敗した枠**（新しいIDが返らないので書き換わらない）

にもかかわらず「繋ぎ直し済み」の目印だけは書かれていた。
次回以降は「変わっていない」と判断されるので、**もう二度と落とされない**。
残った古いIDが処理窓に入った日に「削除された」と判定され、
5件以下なら**一言もなく消える**。繋ぎ直しの数十日後に起きるので、
本人が原因に気づく手がかりが無い。

**どう直したか**

落とす操作を、送信データではなく **localStorage 本体**に対して行うようにした。
順序も入れ替えてある。

```
繋ぎ直しを検知
  → localStorage の全期間の枠から googleEventId を落とす
  → 落とし終えてから目印を書く
  → そのあとで送信（成否は目印に関係しない）
```

目印が意味するのは「この端末に、別カレンダーのIDはもう残っていない」であって、
送信が成功したことではない。IDが空になっている以上、送信が失敗しても
次回は「作り直す」方向にしか倒れず、消える方向には倒れない。

**副産物：目印が永久に null のままになる端末をなくした**

以前は同期の**成功後**にだけ目印を書いていたので、一度も同期に成功していない
端末は目印が null のままだった。`previousCalendarId === null` は
「この端末で初めて同期する」＝落とさない、と判定されるので、
**そういう端末は次に繋ぎ直しても検知できなかった**。
連携状態さえ分かれば目印を書くようにして、この穴も塞いだ。

**関連ファイル**

- [`src/lib/calendar/reconnect.ts`](../../src/lib/calendar/reconnect.ts)
  — `clearEventIdsIfCalendarChanged`（純粋関数）を廃止し、
  `calendarChanged`（判定）と `applyCalendarReconnect`（保存への反映）に分けた
- [`src/components/CalendarSyncBoot.tsx`](../../src/components/CalendarSyncBoot.tsx)
  — 呼び出し順を入れ替え、送信データは「落とし終えたあとの localStorage」から作る

**確認方法**

[`tests/calendar-reconnect.test.mjs`](../../tests/calendar-reconnect.test.mjs) を
書き直した（13件）。要になるのは次の2つで、どちらも修正前のコードでは落ちる。

- 「送信範囲の外にある枠も落とす（+120日）」 … 指摘1そのものの回帰
- 「初回でも目印は書く」 … 上の副産物の回帰

### 2. 重ね表示が、既に連携している本人にだけ永久に出ない（重度：中）

**何が起きていたか**

重ね表示のために `calendar.readonly` を後から足したが、
**OAuthで許可された権限は同意した時点の refresh_token に固定される**。
既に連携済みの人には遡って付かないので、Googleは403を返し続ける。

その403は `listCalendars` が素の `Error` で投げ、ルートが
`{ok:false, message:"カレンダーを読めませんでした。"}` に丸め、
時間割の画面が `ok` が偽だからと `message` を読まずに捨てていた。
結果、**重ね表示は永久に0件のまま、理由がどこにも出ない**。
いちばん影響を受けるのは、この機能を作った本人である。

**どう直したか**

- `GoogleApiError`（HTTPステータスを持ったまま投げる例外）を足し、
  `refreshAccessToken` / `listEvents` / `listCalendars` から投げるようにした
- `needsReconnect(err)` で 401/403 だけを「連携し直せば直る失敗」として区別
- `/api/calendar/overlay` が `{ok:false, reason:"reconnect_required", message}` を返す
- 時間割の画面は、それを受けたら帯を出し、端末に印を残す
- 設定画面の連携ブロックは、その印を読んで「読み取りの許可が足りません」と
  「連携し直す」ボタンを出す

通信障害や5xx・レート制限は今までどおり「読めませんでした」に丸める。
**再連携で直らない失敗を「連携し直してください」と案内しない**ためで、
ここを分けないと案内そのものが信用されなくなる。

### 3. refresh_token の重みが変わったのに、前提が更新されていない（重度：中）

`link.ts` には「スコープを calendar.app.created に絞ってあるため、万一漏れても
露出するのは専用カレンダーだけ」と書いてあった。`calendar.readonly` を足した時点で
この前提は失効しており、**いまの refresh_token は本人の全カレンダーの
全予定を読める鍵**である。書き換えられないのは今も正しいが、読まれないとは言えない。

コードの動作は変えていない。`link.ts` と `google.ts` の記述を、
いまのスコープに合わせて書き直した。**設計上の言い訳は、前提が変わったら
必ず書き換える**。ここが古いままだと、今後RLSやキー管理を考えるときに
「大した鍵じゃない」という誤った前提で判断してしまう。

### 4. `/api/calendar/overlay` の入力検証を zod に寄せた（軽微）

AGENTS.md は「APIルートの入力は必ず `api-schema.ts` の zod を通す」と定めているが、
このルートだけインラインの正規表現で日付を見ていた。検証の強さは十分だったが、
置き場所が散らばると抜けても誰も気づけない。`CalendarOverlayQuerySchema` に移した。

### 5. `/me` の「はじめて0日目」——**原因は日付のバグだった**（R2）

`残件.md` R2 は「習慣を完了した直後でも『はじめて0日目』と出る。
14日たつまで統計を出さないのは意図した設計に見えるので、勝手には直さなかった」
としていた。**調べたら、少なくとも半分は設計ではなく不具合だった。**

`createdAt` は `toISOString()` の**UTC**文字列なのに、
`habit.createdAt.slice(0, 10)` で日付として使っていた。
AGENTS.md が明示的に禁じているやり方で、JSTでは朝9時までが前日になる。

実際に次の2つの形で表に出ていた。

- **深夜〜朝（JST 00:00〜08:59）に作った習慣は、作った瞬間に「1日目」になる。**
  それ以外の時間に作れば「0日目」。同じ操作でも作った時刻でぶれる
- `computeStreak` / `computeRate` のコメントは「作成日そのものも数えない」と
  書いてあるのに、**早朝に作った習慣だけ作成日が数えられていた**

`habitStartDate()` を足して、瞬間（UTC）をこの端末の暦の日に直してから
比べるようにした。3箇所すべてを通してある。

**この修正で表に出る変化（重要）**

早朝に作った習慣は、これまで作成日の記録がストリークに数えられていたが、
**数えられなくなる**（＝他の時間に作った習慣と同じ扱いになる）。
「作成日は数えない」という既存の意図に揃えただけで、方針は変えていない。
ただし結果として、**作った当日に「できた」を押しても
`/me` の連続日数は0のまま**になる。これは R2 の後半
（押した手応えを返すか）そのものなので、**方針の判断は残してある**（下記）。

あわせて、日本語として言わない「はじめて0日目」は当日だけ
**「今日つくったばかりです。」**に変えた。14日の待ち時間そのものは触っていない。

**確認方法**

[`tests/habit.test.mjs`](../../tests/habit.test.mjs) に5件足した
（ファイル先頭で `TZ=Asia/Tokyo` を固定）。うち3件は修正前のコードでは落ちる。

## 実機での動作確認

`残件.md` R4 は「単体テストはあるが、実機の指の操作は一度も通していない。
定期タスクのセッションではブラウザペインが開けない」として空いていた穴だった。
**今回はブラウザで実際に操作して埋めた。**

開発サーバー（`localhost:3000`）に対して、まっさらな localStorage の状態から

経由していない**。ここだけは指で1回触るのがいちばん早い。
