## 1. 直した不具合

### 症状

ログイン中に目標を消し、**その 1.5 秒以内にタブを閉じる／リロードする／回線が切れる**と、
クラウド側にその目標の予定枠が「どの目標にも紐づかない枠」として残る。
あとで別の端末を繋ぐ、または設定画面の「置き換える」で取り込むと、
**目標ごと消したはずの予定が時間割に戻ってくる**。

データが壊れるわけではない（もともと消すはずだったものが残るだけ）。
同じ端末でもう一度同期が走れば自動で片付く。ただし本人には
「消したものが勝手に戻ってきた」としか見えない。

### なぜ起きていたか

目標を消すと、保存は3本走る。ここで**送られ方が揃っていなかった**。

| 書き込み | クラウドへの送られ方 |
|---|---|
| `gc.cards`（目標そのもの） | **すぐ送る** |
| `gc.habitlogs`（習慣の記録） | すぐ送る |
| `gc.habits`（習慣） | **1.5秒待つ** |
| `gc.timeboxes`（予定枠） | **1.5秒待つ** |

1.5秒待つのは、2026-09-10 に入れた「1文字打つたびに全件送信しない」ための仕組み
（`push-queue.ts` の末尾デバウンス）である。予定シートと習慣の編集は
保存ボタンを押させない作りなので、打ち終わりを待ってから1回だけ送る。

ところが**消すときだけは、この「待ち」が裏目に出る**。
クラウド側の外部キーは、目標の行が消えると
`timeboxes.card_id` を **SET NULL にするだけで行は残す**（`habits` は連鎖で消える）。
つまり「目標を消した」はすぐ届き、「枠も消した」は1.5秒遅れて届く。
その隙間でタブが閉じると、**クラウドに枠だけが取り残される**。

閉じる瞬間に送り切る仕組み（`SyncBoot` の `pagehide` / `visibilitychange`）は
あるが、実際に閉じるときは送信が間に合わないことがある。

### どう直したか

**目標を消す操作だけ、待ちを解いてから終わる**ようにした。
消す操作は連打されるものではないので、まとめる利点がそもそも無い
（`push-queue.ts` が「キーを丸ごと消した書き込み」を最初から素通しさせているのと同じ理屈）。

`storage.ts` は同期の中身を知らないままにしておきたいので、
`setSyncHook` と同じ形で **`setSyncFlushHook`**（待ちを解いてほしいと頼む口）を足し、
`sync.ts` 側が `pushQueue.flush()` を繋ぐ形にした。
ログインしていなければ待ち行列は空なので、呼ばれても何も起きない。

```
deleteCard()
  ├ gc.cards      を書く（すぐ送る）
  ├ gc.habits     を書く（待ちに乗る）
  ├ gc.habitlogs  を書く（すぐ送る）
  ├ gc.timeboxes  を書く（待ちに乗る）
  └ onSyncFlushHook() ← 追加。待っているぶんを、ここで送り切る
```

### 直した範囲（どこまでが対象か）

**対象にしたのは `deleteCard()` だけ**である。理由を明記しておく。

- `deleteCard()` だけが、**すぐ送る書き込みと待つ書き込みを混ぜている**。
  先に届いた `gc.cards` がクラウド側で連鎖を起こすので、
  後続が届かないと「クラウドにだけ残る行」という食い違いが生まれる。
  ほかの操作にはこの非対称が無い。
- `deleteTimeBox()`（予定を1件消す）は `gc.timeboxes` しか書かないので、
  届かなくても食い違いは起きない（クラウドに古い枠が残るだけで、
  次にその端末が同じキーを書けば追いつく）。
  こちらに `flush` を入れると、カレンダー同期が削除をまとめて処理する
  `CalendarSyncBoot`（`for (const id of data.deletes) deleteTimeBox(id)`）で、
  **消した件数ぶん全件送信が走る**。今回は入れず、残件に書いた。
- `archiveHabit()`（習慣をやめる）は消す操作ではなく更新なので、
  遅れてもクラウド側に矛盾は生まれない。
- `deleteSnapshot()` はその端末だけの保存なので、クラウドと無関係。

| もう一度完了 → 枠を「この予定を消す」 | 枠と一緒に `done` も取り消される | 取り消された |

## 残っていること

- **判断待ち7件**（R1・R2'・R3・R10・R11・R12・R13）と、
  設定画面の「置き換える」が待機中の編集を捨てる件。上の §3 のとおり。
- **`deleteTimeBox()`（予定を1件だけ消す）も同じ窓を持っている。** 優先度は低い。
  消した直後にタブを閉じ、別端末で取り込むと、その枠だけが戻ることがある。
  同じ端末で次に時間割を触れば自動で片付く。
  直すなら `CalendarSyncBoot` の一括削除ループで全件送信が繰り返されないよう、
  「ループの終わりで1回だけ送り切る」形にする必要がある。
- **今回の修正のクラウド側での効果は未確認**（R6 と同じ理由）。
  ログインできる状態になったら、「目標を消す → すぐリロード →
  設定画面で『置き換える』→ 目標に紐づかない枠が出ないこと」で確かめられる。
