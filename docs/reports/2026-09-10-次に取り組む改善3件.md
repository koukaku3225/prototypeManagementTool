## 改善1（最優先）: woop_wbs のターン上限が、問い直し1回で「いつ・どこで」を取り切れずに強制完了しうる

### 現在の問題

**目標対話を最後の `woop_wbs`（障害と明日の一歩）まで進めた利用者**が、
「明日の何時に」「どこで」の答えが少しでも曖昧で、コーチが**問い直しを1回でも挟むと**、
その手前でシステムが強制的にフェーズを打ち切る。結果、対話の唯一の持ち帰りである
**「明日、何時に、どこで、何をやるか」が時刻または場所の欠けた状態で確定**する。

`woop_wbs` の指示文（`src/lib/prompts/phases.ts:161-193`）は、次の5手を「順に、1つずつ」求める。

1. つまずきそうな場面（障害）
2. 障害が起きる具体的な状況
3. If-Then を**本人に作らせる**（曖昧なら「直さずに、どこが曖昧かだけ指摘して問い直す」。
   最大2回まで問い直す）
4. 作業を3〜5個挙げさせ、明日45分以内の1つを選ばせる
5. 選んだ1件の「いつ」と「どこで」を決めさせる
   （「『夜』は何時ごろですか」「『家で』なら『家のどこですか』まで具体にする」= **問い直し前提**）

### 根拠

- `src/types/goal.ts:31-43` — `PHASE_TURN_LIMIT.woop_wbs = 7`。
  コメントは「5 のままだと最後の『いつ・どこで』を聞く手前で強制遷移してしまい、
  実行意図が空のまま完了する（実機で確認した不具合）。問い直し1回ぶんの余裕を見て 7」。
- `src/app/api/chat/route.ts:100-105` — `resolvePhase` を `turnsInPhase: body.turnsInPhase + 1`
  で呼ぶ。モデルの N 回目の返答時に `N >= 7` なら強制遷移。
- `src/lib/phase-machine.ts:94-96` — `turnsInPhase >= turnLimit` なら
  `claimed` に関係なく `{ phase: 次, forced: true }` を返す。
- ターンの数え方（`AGENTS.md` / `src/types/goal.ts:85-88`）:
  各フェーズ**最初のアシスタント発言（問いかけ自体）がユーザー未回答で1ターン消費**する。
  したがって `woop_wbs` の内訳は次のとおり。

  | 返答 | 内容 |
  |---|---|
  | 1 | フェーズの口火（障害を聞く） |
  | 2 | ← 障害の答え |
  | 3 | ← 状況の答え |
  | 4 | ← If-Then の文 |
  | 5 | ← タスク選択 |
  | 6 | ← 「いつ」の答え |
  | 7 | ← 「どこで」の答え。**ここで `7 >= 7` により強制遷移**（`forced: true`） |

  **問い直しゼロ・時刻も場所も一発で確定**したときだけ、ちょうど収まる。
  指示文が想定している問い直し（If-Then に最大2回、時刻・場所に各1回）が
  1つでも起きると、「どこで」の答えが返答8回目以降にずれ込み、
  6〜7回目の「まだ質問している」状態で打ち切られる。
- `src/hooks/useConversation.ts:257-262` — `forced` でも自動遷移はせず `pendingForced` になり、
  利用者は「次へ」ボタンを見る。コーチの最後の発言は**問いのまま**。
- `src/app/card/page.tsx` — 対話完了後、`/api/structure` が会話全文から「明日の一歩
  （タイトル・所要時間・開始時刻・場所）」を抽出し、`confirm()` が**時間割の枠を1件作る**。
  会話に時刻・場所が無ければ、枠にも入らない。
- `tests/phase-machine.test.mjs:49` は `smart` の上限5を固定しているが、
  **`woop_wbs` の上限7を固定するテストは無い**。将来また縮んでも気づけない。

### 提案（最小限）

1. `src/types/goal.ts` の `PHASE_TURN_LIMIT.woop_wbs` を **7 → 10** にする（コメントも更新）。
   - 問い直し約3回ぶんの余裕。small フローの最大は 16 → 19 ターン。
     廃止した5フェーズ39ターンの半分で、`mvp-spec` の「長すぎる」への懸念には十分収まる。
2. `tests/phase-machine.test.mjs` に **`woop_wbs` の上限を固定する回帰テスト**を足す。
   - 「返答9回目（`turnsInPhase:9`）ではまだ `forced` にならない」
   - 「返答10回目（`turnsInPhase:10`）で `forced: true`」
   - 「`claimed:'done'` を返せば上限前に `forced:false` で `done` へ」
3. （任意・別案）`resolvePhase` で「`woop_wbs` から強制遷移するとき、
   直前のアシスタント発言が問いで終わっていれば1ターンだけ猶予する」猶予ロジック。
   ただし `resolvePhase` の引数が増えるので、まずは 1 の値変更だけを推す。

### 優先する理由

- **対話の成果（30〜40分）を、最後の1〜2問で台無しにしない。** 「明日の一歩」は
  アプリの全機能（時間割・NowBar・習慣・振り返り）の起点。
- 変更は定数1つ＋テスト。回帰は `resolvePhase` の純粋関数テストで固定できる。
- `AGENTS.md` が名指しで警告している落とし穴（「`PHASE_INSTRUCTIONS` に手順を足したら
  `PHASE_TURN_LIMIT` も必ず見直す。型でもテストでも捕まらない」）そのもの。

### 完了条件

- [ ] `woop_wbs` で問い直しが2回入っても、「いつ・どこで」を答え切る前に強制遷移しない。
- [ ] `tests/phase-machine.test.mjs` が `woop_wbs` の上限を固定し、縮めると落ちる。
- [ ] `npm test` / `npx tsc --noEmit` / `npm run build` が通る。

## 改善2: 未ログイン利用者に「この端末にしか残っていない」ことと書き出し導線が届いていない

### 現在の問題

**ログインせずに使っている利用者**（今はログイン任意）にとって、
デプロイ済みのアプリでは**自動バックアップが一切効かない**。
対話全文・目標・習慣・時間割は、そのブラウザの localStorage にしか無く、
「サイトデータを消去」やプライベートモードの終了で**まとめて消える**。
`AGENTS.md` は「localStorage が丸ごと消えた実例がある」と、本人の実データが
消えた事故を明記している。

`src/components/LocalBackupBoot.tsx` のディスク書き込みは
**「`npm run dev` のローカル環境専用」**（`AGENTS.md` 明記、サーバーレスでは
ディスクが永続しない）。つまりデプロイ環境で未ログインの間、安全網はゼロ。

いまの緩和策：
- `/me` にログインCTA（未ログイン時のみ、`me/page.tsx:79`）… ログインを促してはいる
- `設定 > 書き出し / 読み込み` に JSON 書き出し（`settings/page.tsx:334-364`）
  … BottomNav →「わたし」→「設定」→ スクロール、と**4手先**。自発的にたどり着く導線がない

### 根拠

- `AGENTS.md`「localStorage が丸ごと消えた実例がある」「これは `npm run dev` の
  ローカル環境専用」。
- `src/components/LocalBackupBoot.tsx` — `/api/local-backup` はローカルディスク
  （`.local-backups/`）。デプロイ環境では機能しない。
- `src/lib/supabase/sync.ts` — Supabase 同期は**ログイン時のみ**。未ログインは `off`。
- `src/app/settings/page.tsx:334` — 書き出しは「設定」画面の下部セクションのみ。
  `me/page.tsx` の「そのほか」にも書き出しへの直リンクは無い。
- `src/lib/storage.ts` `captureState()` / `src/lib/export.ts` `download()` は既にあり、
  ボタンを増やすだけで再利用できる。

### 提案（最小限）

新機能は作らず、**既にある `captureState()` + `download()` を、未ログインの利用者の
目に入る場所に1つ出す**。次のどちらか（Aを推す）。

- **案A（小）**：`/me` のログインCTAのすぐ下（未ログイン かつ 中身がある とき）に、
  1行の注意と「いま書き出す」ボタンを置く。
  文言例：「ログインしない場合、データはこの端末にしか残りません。
  ときどき書き出して保管してください。」
- **案B（小〜中）**：`gc.lastExportAt` を localStorage に持ち、
  「前回の書き出しから N 日以上」かつ「中身が増えている」ときだけ
  `/plan` か `/me` の上部に帯を出す（×で消せる）。判断の量が増えるぶん設計の相談が要る。

`gc.lastExportAt` を足す場合、`captureState()` が丸ごと送る仕様なので
`SNAPSHOT_TARGETS` の変更は不要（`AGENTS.md`）。同期は不要（端末ローカルの概念）。

- **中心価値そのものが、事故1回で消える**。対話でしか作れないデータ（過去の挫折・価値観）は
  復元不能。ログインを待たずに打てる手。

## 改善3: 習慣を作った当日に「できた」を押しても、連続日数にも達成率にも反映されない（R2' の具体案）

### 現在の問題

**朝〜昼に習慣を作り、その日のうちに実行した利用者**が、`/me` を開いても
「今日つくったばかりです。」としか出ず、**連続日数は 0、達成率も対象外**。
`/list` の「今日の習慣 1/1」には出るので押した記録は残るが、
`/me` の「いまのところ N 日続いています」は N=0 で表示されない。
習慣化はいちばん最初の数日の手応えで決まるのに、初日の成功が数字に一切乗らない。

`残件.md` R2' で「作成日は数えない」を既存コードの明示的な意図として竜一に判断を
委ねている箇所。今回、**副作用の小さい具体案（C）**まで詰めた。

### 根拠

- `src/lib/habit.ts:89` `computeStreak` … `if (date <= start) break;`
  （作成日そのものを数えない）
- `src/lib/habit.ts:131` `computeRate` … 同じく `if (date <= start) break;`
- `src/lib/habit.ts:43` `habitStartDate` … 9/9 に UTC 切り出しバグは修正済み。
  いまは全時間帯で作成日が揃っている＝**当日は必ず対象外**で一貫している。
- `src/app/me/page.tsx:189` … `days <= 0` のとき「今日つくったばかりです。」
- コメントの意図（`habit.ts:126-131`）:「夜に作った習慣を、その日のうちに
  『できなかった』と数えるのは筋が通らない」。**これは missed を数えたくないという話**で、
  done を数えたくないという話ではない。

### 提案（最小限）＝ 案C

「**作成日は、その日に `done`／`partial` の記録があるときだけ数える**」。

- `computeStreak` / `computeRate` の `if (date <= start) break;` を、
  `date < start` で break（作成日より前で止める）に変え、
  `date === start` の反復では「記録があって `kept` のときだけ集計、
  無い／missed なら**その日はスキップ**（分母にも入れない）」にする。
- 案B（作成日を無条件に予定日扱い）と違い、
  **夜に作ってやらなかった習慣が、その日いきなり達成率0%に落ちることはない**。
- `me/page.tsx` の当日文言を「今日つくって、1回できました。」のように
  記録の有無で出し分ける。

### なぜ判断を委ねるか

- 純粋関数の分岐が1つ増える。`tests/habit.test.mjs` の既存ケース
  （「作成日は数えない」を前提にしたもの）を読み直して整合を取る必要がある。
- 「初日を数えるかどうか」は習慣化の設計思想の問題で、竜一の見立てを聞きたい。
- `WARMUP_DAYS`（14日）そのものは、案Cでも触らない。

### 完了条件

- [ ] 朝に作った習慣を当日「できた」にすると、`/me` の連続日数が 1 になる。
- [ ] 当日やらなかった習慣は、達成率が 0% にならない（分母に入らない）。
- [ ] `tests/habit.test.mjs` に「作成日＋done → streak 1」「作成日＋記録なし → 対象外」。
- [ ] 既存の習慣テストがすべて通る。

### 確認方法

- 単体：`computeStreak` / `computeRate` に作成日ケースを追加。
- 手動：習慣を作り、当日「できた」→ `/me` で「1日連続」。別の習慣は当日放置 →
  達成率が「—」のまま（0% にならない）。

### 規模

**小〜中**。変更対象：`src/lib/habit.ts`、`src/app/me/page.tsx`、`tests/habit.test.mjs`。

## 仕組みの説明（改善1）

対話は「大きな物語（big：理想像→なぜ大事→立ち位置、最大10ターン）」→
「small：理想の姿（diverge）→ 具体化（smart）→ 障害と明日の一歩（woop_wbs）」の順で進む。

`woop_wbs` は「障害 → 状況 → If-Then → タスク選び → いつ・どこで」の5手を、
1問ずつ聞く設計。各フェーズには「堂々巡り防止」の**ターン上限**があり、
超えるとモデルの意思に関係なくシステムが次へ送る（`forced`）。

```
現状:  woop_wbs の上限 = 7
       = 「口火(1) + 障害・状況・IfThen・タスク・いつ・どこで の6答」ちょうど
       → 問い直しが1回でも入ると「どこで」を聞く前に打ち切られる

提案:  上限 = 10（問い直し約3回ぶんの余裕）
       + 上限値を固定する回帰テスト（次に縮めたら落ちる）
```

`forced` になっても画面は自動で切り替わらず（`useConversation.ts:257`）、
利用者は「次へ」を押して初めて進む。だが**コーチの最後の発言は問いのまま**で、
`/api/structure` はその不完全な会話から「明日の一歩」を抽出する。
