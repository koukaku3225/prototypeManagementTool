## 指摘1（重度：中の下）`needsReconnect()` が 403 を一律「再連携で直る」と判定し、誤った案内を端末に焼き付ける

**ファイルと行**

- [src/lib/calendar/google.ts:78-82](src/lib/calendar/google.ts) `needsReconnect()` … `status === 401 || status === 403` だけで判定
- [src/lib/calendar/google.ts:135-140](src/lib/calendar/google.ts) `refreshAccessToken` … 非ok時に `GoogleApiError(res.status)` を投げる
- [src/app/api/calendar/overlay/route.ts:108-115](src/app/api/calendar/overlay/route.ts) `needsReconnect(err)` なら `reason:"reconnect_required"`
- [src/app/plan/page.tsx:171-173](src/app/plan/page.tsx) `reason === "reconnect_required"` で `writeDeviceFlag(calendarNeedsReconnect, "1")`
- [src/components/CalendarLink.tsx:47-51](src/components/CalendarLink.tsx) その印を読んで「読み取りの許可が足りません」＋再連携ボタンを常時表示

**発生条件**

`GET /api/calendar/overlay` の中で Google が **403 または 401 を、権限不足以外の理由で**返したとき。具体的には次の2つ。

1. **レート制限・クォータ超過（403）。** Google Calendar API は
   `rateLimitExceeded` / `userRateLimitExceeded` を **HTTP 403** で返す
   （429 に統一されていない）。重ね表示は1回の描画で `listCalendars` 1回＋
   `listEvents` を最大8回叩き、時間割で日付を送るたびに走る。日付を素早く
   めくると短時間に往復が集中しうる。コミットは「レート制限は今までどおり
   丸める」と宣言し、テストも `GoogleApiError(429)` だけを false と確認して
   いるが、**403 のレート制限は拾えていない**。
2. **リフレッシュトークンの失効（`invalid_grant`）。** これは OAuth の
   トークンエンドポイントが **HTTP 400** で返す（RFC 6749 §5.2、Google も準拠）。
   `refreshAccessToken` は `GoogleApiError(400)` を投げ、`needsReconnect` は
   false を返す。**「再連携が必要」の最も一般的な原因（本人が Google 側で
   アクセスを取り消した／トークン期限切れ）で、この機能が追加した専用の
   案内が出ない**（従来どおりの「カレンダーを読めませんでした」に丸まる）。

なお、購読カレンダー個別の 403（共有解除など）は
`Promise.allSettled`（overlay/route.ts:74-91）が握るので外側の catch には
来ない。問題になるのは `listCalendars` / `refreshAccessToken` の失敗。

**利用者への影響**

- ケース1：一時的なレート制限で、「読み取りの許可が足りません。連携し直して
  ください」という**再連携しても直らない案内**が時間割と設定画面に出る。
  印（`gc.calendarNeedsReconnect`）は localStorage に残り、**次に重ね表示が
  成功するまで消えない**。コミットが避けたいと明言した
  「案内そのものが信用されなくなる」状態そのもの。
- ケース2：本当に再連携が要る場面で、追加した案内が出ない。実害は
  「従来と同じ」に留まる（設定画面の `state.lastError` には同期側のエラーが
  出る可能性がある）が、`needsReconnect` という名前の関数が主要な
  reconnect 要因を取りこぼしている。

**修正候補**

- `GoogleApiError` にレスポンスボディの `error.errors[].reason`
  （`insufficientPermissions` / `authError` など）や `error` 文字列
  （`invalid_grant`）を持たせ、`needsReconnect` を
  「403 かつ reason が権限系」「トークン更新失敗かつ `invalid_grant`」に
  絞る。単なる 403（レート制限・バックエンド不調）は false のまま。
- 当面の簡便策としては、少なくとも `refreshAccessToken` の失敗時に
  ボディを見て `invalid_grant` を拾う分岐を足す。403 レート制限の誤検知が
  怖ければ、`needsReconnect` を 401 と「403 かつ権限系 reason」に限定する。

**確認方法**

1. `tests/calendar-overlay.test.mjs` に
   「403 のレート制限（reason=`rateLimitExceeded`）は `needsReconnect` false」
   「トークン更新の `invalid_grant`（status 400）は true」を追加 → 現状は落ちる。
2. 実機では、`refreshAccessToken` を一時的に 400 `{error:"invalid_grant"}` を
   返すようモックし、overlay が `reconnect_required` を返さないことを確認。

## 指摘2（重度：中の下→低）繋ぎ直しの検知が誤爆すると、localStorage の `googleEventId` が全件・恒久的に落ちる

**ファイルと行**

- [src/lib/calendar/reconnect.ts:74-108](src/lib/calendar/reconnect.ts) `applyCalendarReconnect` … `changed` なら `storage.loadAll()` 全件に対し `save({...b, googleEventId:null})`、その後 `writeFlag`
- [src/components/CalendarSyncBoot.tsx:53-78](src/components/CalendarSyncBoot.tsx) `currentCalendarId = status?.calendarId ?? null` を渡す
- [src/lib/calendar/reconnect.ts:49-56](src/lib/calendar/reconnect.ts) `calendarChanged` … `previousCalendarId !== null && previousCalendarId !== currentCalendarId`

**発生条件**

`GET /api/calendar/status` が返す `calendarId` が、`gc.lastCalendarId` に
保存済みの値と**異なる**とき。正規の繋ぎ直しでは正しい挙動。誤爆の条件は
「status が過去に一度正しい値を書いたあと、別の値（空でない誤った id、
別アカウントの id、実装変更による id 形式の変化など）を返す」こと。

**利用者への影響**

- 今回の変更で、ID を落とす対象が「送信用配列」から
  **localStorage 本体（全期間・全件）**に広がった。これは意図した修正
  （送信窓の外の枠に古い ID が残る穴を塞ぐ）だが、副作用として
  **誤爆時の代償も大きくなった**。
  - 変更前：誤爆しても localStorage の実 ID は無事で、次回 status が
    正しい値を返せば自己回復した。
  - 変更後：誤爆した瞬間に全枠の `googleEventId` が null になり、目印も
    新カレンダーに書き換わる。次回以降は `changed=false` で回復しない。
    送信窓内の枠は Google 側に**重複予定**として作り直され、窓外の枠は
    ID を失ったまま（後日窓に入った時点で作り直し＝そこでも重複）。
- 前回指摘1（送信窓外の穴）を確実に塞ぐための変更なので方向性は妥当。
  リスクは「status の calendarId がどれだけ信用できるか」に依存する。
  `link.calendarId` は再連携以外で変わらない想定なので、**現実の誤爆確率は
  低い**。重度は「低」寄り。

**あわせて（さらに低）**：クリアのループは `upsertTimeBox` を1件ずつ呼び、
`write()` は容量超過を握りつぶして例外を投げない。保存に失敗した枠が
残ったまま `writeFlag` が走ると、「片付いた」目印だけが残り、
一部の枠に古い ID が残存する——コミットが塞いだ穴と同じ形が、
ストレージ逼迫時に再発しうる。コード内コメントは順序（目印を最後）には
言及しているが、ループ内の部分失敗には触れていない。

**修正候補**

- `calendarChanged` を「前回値が非 null かつ現在値と異なる」だけでなく、
  「現在値が status 取得に**成功**して得られたもの」に限定する
  （`res.ok` が false のときは status が null になる実装なので概ね担保
  されているが、`status` が ok でも `calendarId` が想定外の値のときの
  ガードは無い）。誤爆時の影響範囲を送信窓（例：-14〜+90 日）＋
  「window 外は次回送信時に個別判定」に留める案も検討に値する。
- クリアのループで `upsertTimeBox`（＝`write`）の戻り値が false の件が
  1件でもあれば `writeFlag` をスキップし、次回に再試行させる。

**確認方法**

1. `tests/calendar-reconnect.test.mjs` に
   「`save` が一部の枠で false を返したら `writeFlag` しない」を追加。
2. 「`changed=true` で全期間の枠（送信窓外を含む）の ID が落ちる」ことは
   既存テストで確認できるはず。誤爆時の回復不能性は設計判断としてレビューに残す。
