## 確認内容（問題なしと判断）

### `0455aed` 再連携の誤検知の解消（`needsReconnect` / `GoogleApiError.reason`）

- [src/lib/calendar/google.ts](src/lib/calendar/google.ts) `readErrorReason()` はレスポンス本文の
  JSONパースに失敗しても例外を握って `null` を返す（成功パスでは呼ばれないため二重読み取りの心配もない）。
- `needsReconnect()` の分岐（`invalid_grant` → true、401 → true、403は理由がレート制限系集合に
  含まれなければ true）はテスト（`tests/calendar-overlay.test.mjs:170-296`）で境界値ごと網羅されている。
  許可リストでなく除外リストにした理由（Google側の理由文字列の揺れ）も筋が通っている。
- 403の理由集合（`RETRYABLE_403_REASONS`）はGoogle Calendar APIの公開エラーコード
  （`rateLimitExceeded` 等）に基づく一般的な分類で、アプリ固有の当てずっぽうではない。

### `0455aed` 繋ぎ直し後始末の部分失敗（`applyCalendarReconnect` / `upsertTimeBox`）

- `upsertTimeBox()` の戻り値を `void → boolean` にした変更は、内部の `write()` が既に
  `boolean` を返していたための素直な配線で、既存の呼び出し側（戻り値を使わない箇所）は
  型・挙動とも影響なし（`grep` で全呼び出し元を確認）。
- `applyCalendarReconnect()` は1件でも保存に失敗したら目印を書かない、というテスト
  （`tests/calendar-reconnect.test.mjs:249,269,281,290`）で確認済み。

### `411703e` 完了取り消しで習慣記録も取り消す（`clearHabitLogFromBox`）

- `state !== "done"` または `at` が不一致なら何もしない、という絞り込みはテスト4件
  （`tests/storage.test.mjs:556-581`）で確認。手動記録・他状態への誤爆はない。
- `saveBox`（`list/page.tsx` `plan/page.tsx`）の呼び出しは、削除前に取得した `before`
  （state変数 `boxes` からの参照）の `completedAt` を使っている。日付が変わるケースを
  懸念したが、`TimeBoxSheet` の `draft` に日付を変更する入力経路がなく（`grep` で確認）、
  `real.date === before.date` が常に成立するため、日付をまたぐ取り違えは起きない。
- `deleteTimeBox()` に追加された自動清算は `CalendarSyncBoot` の一括削除ループ
  （カレンダー側で消えたイベントの反映）からも通る。意図的な仕様（完了済み枠が消えれば
  記録も消える）と読め、コミットメッセージの記述とも一致するため問題としては扱わない。

### `0bad5ae` 目標削除時のflush（`setSyncFlushHook`）

- `deleteCard()` 末尾で `onSyncFlushHook?.()` を呼ぶだけの変更で、`sync.ts` 側は
  モジュール読み込み時に無条件で `setSyncFlushHook(() => pushQueue.flush())` を繋ぐ。
  未ログイン時は待ち行列が空のため空振りする、という説明どおりの実装。
- 既存の `flushPendingPushes()`（`SyncBoot` の `pagehide`/`visibilitychange` 用）と同じ
  `pushQueue.flush()` を呼ぶだけなので、新しい失敗経路は増えていない。
- 前回レビュー指摘1が要求した「削除は待たせない」を過不足なく実装しており、対応漏れはない。
