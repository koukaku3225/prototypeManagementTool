# 同期が黙って止まっていた件 — 原因と対処

作成日: 2026-09-06

## 結論

**クラウドへの保存が失敗し続けていたのに、本人に伝わっていなかった。**

原因は1つではなく、3つが重なっていた。

1. `timeboxes`（時間割）の保存だけが Supabase に弾かれ続けていた
2. その理由が `[object Object]` と表示され、**読めなかった**
3. 失敗を知らせるのが**設定画面だけ**で、日常的に開く時間割画面には何も出ていなかった

結果、別の端末で開いたときに「予定が何も無い」形で初めて発覚した。

## 背景

「ブラウザによって表示される予定が違う」との報告を受けて調査した。

- ブラウザA: `/plan` が 予定0分（空）
- ブラウザB: `/plan` に 12時間12分・11件

## 調査結果（事実）

Supabase の `timeboxes` は **13件、最新は 2026-09-05**。

```
09-05 22:15  アプリ制作をやりましょう。   ← クラウドで一番新しい
09-05 21:45  マッチングアプリでいいねしへ返信
09-04 21:30  アプリリリースに向けて開発
```

一方、ブラウザBが表示していた **09-06 の11件**（「ミン卓」「向井サークル」
「奴らと飯に行く」など）は、**クラウドに1件も無い**。

つまり **ブラウザAは正しい**。クラウドに無いものは表示できない。
壊れていたのは「ブラウザB → クラウド」の保存だった。

設定画面にはこう出ていた:

```
自動で同期しています
直近の同期エラー: 同期に失敗しました（gc.timeboxes）: [object Object]
```

状態は `ready`（正常）なのに、`timeboxes` の保存だけが失敗し続けていた。

### 最初の推測は外れた

当初は「端末とクラウドの両方に中身があるため保存を止めている（conflict）」
状態だと推測したが、設定画面のスクリーンショットが `ready` を示していたため
**誤りと判明した**。推測ではなく画面の表示が正解を示した。

## 直したこと

### 1. エラーが読めるようにした（`sync.ts`）

Supabase のエラーは `Error` のインスタンスではなく
`{ message, details, hint, code }` を持つただのオブジェクトである。
そのため `String(err)` が `"[object Object]"` になり、画面にもコンソールにも
理由が一切残らなかった。

`describeError()` を追加し、`message / details / hint / code` を連結して出す。
文字列化できない場合は `JSON.stringify` に落とす。

**原因が読めない失敗は、無いのと同じくらい質が悪い。**

### 2. 書き込み順を入れ替えた（`sync.ts` の `reconcileCollection`）

これまでは **delete → upsert** の順だった。upsert が失敗すると、
削除された行が戻らないまま終わる（＝データ消失）。

**upsert → delete** に変更した。この順なら:

- upsert が失敗しても、消えたものは無い
- delete が失敗しても、余分な行が残るだけで次の同期で片付く

**失うより、余るほうがましである。**

今回は削除対象が無かったため実害は出ていないが、順序として誤っていた。

### 3. 保存が止まったことを全画面に出す（`SyncStalledBar.tsx`）

設定画面にしか出していなかった案内を、**どの画面にいても見える帯**にした。

出す条件は「本人が動かないと直らない状態」に絞ってある。

- `conflict`（どちらを残すか選ぶ必要がある）
- `failed`（同期の向きを決められなかった）
- **直近の保存が失敗している**（状態は `ready` でも出す）

3つ目が今回の穴だった。状態だけを見ていると、
「正常なのに個々の保存が失敗し続ける」を取りこぼす。

エラー内容もそのまま帯に出す。原因が読めないと本人も直しようがない。

購読のために `sync.ts` へ `onSyncError()` を追加した。

## 検証

- `npx tsc --noEmit` エラーなし
- `npm test` 全通過（111ファイル走査）
- 警告帯が**実際に描画されること**を確認した。条件を一時的に反転して
  `/plan` に表示されること（`sticky` で上部固定、「設定で直す」ボタン付き）を
  ブラウザで確認し、元に戻して再度テストを通した

## 残件

### 根本原因（`timeboxes` が弾かれる理由）は未特定

エラーが読めるようになったので、**次回の保存で理由が画面に出る**。

有力な仮説: `timeboxes.id` 列は `uuid` 型だが、
古い「次の一歩」からの移行が作るIDは `from-task-<uuid>` 形式で、
UUIDとして無効。1件でも混ざると **バッチ全体が弾かれる**
（`'habit-abc-2026-09-06'::uuid` が
`invalid input syntax for type uuid` になることは実測で確認済み）。

他の保存経路（打刻・手動作成・習慣からの実体化）はすべて
`crypto.randomUUID()` を使っており問題ない。

確認するには、ブラウザBのコンソールで次を実行する:

```js
JSON.parse(localStorage.getItem('gc.timeboxes')||'[]')
  .map(b => b.id)
  .filter(id => !/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i.test(id))
```

空配列でなければ仮説が当たり。その場合の対処は、
移行処理が作るIDをUUIDにするか、送信前に弾く。

### この修正はまだ本番に出ていない

`feat/google-calendar-sync` ブランチ上にある。
本番反映後に、ブラウザBで警告帯とエラー内容を確認する。
