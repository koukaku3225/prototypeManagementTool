## 指摘1（重度：中の下）目標削除の直後1.5秒以内にタブが閉じると、クラウドに `card_id=null` の孤児 timebox が残り、次の取り込みで「目標に紐づかない予定枠」として復活する

**ファイルと行**

- [src/lib/storage.ts:471-480](src/lib/storage.ts) `deleteCard()` … `write(KEY.cards, …)`（即送信）→ `deleteHabitsOfCard()` → `deleteTimeBoxesOfCard()`
- [src/lib/storage.ts:630-635](src/lib/storage.ts) `deleteTimeBoxesOfCard()` … `write(KEY.timeboxes, filtered)`（**null ではなく絞り込んだ配列**）
- [src/lib/supabase/sync.ts:122-125](src/lib/supabase/sync.ts) `pushQueue` … `debounced: [KEY.timeboxes, KEY.habits]`
- [src/lib/supabase/push-queue.ts:80-91](src/lib/supabase/push-queue.ts) `push()` … `value === null` のときだけ即送信。配列は 1.5 秒待つ
- [src/components/SyncBoot.tsx:24-37](src/components/SyncBoot.tsx) `pagehide` / `visibilitychange` で `flushPendingPushes()`
- クラウド側の外部キー（`pg_constraint` で確認）
  - `habits_card_id_fkey` … **CASCADE**（目標を消すと習慣も消える）
  - `timeboxes_card_id_fkey` … **SET NULL**（目標を消すと `card_id` が null になり、行は残る）
  - `timeboxes_habit_id_fkey` … **SET NULL**

**発生条件**

ログイン中（push 有効）に目標を削除し、**その 1.5 秒以内にタブを閉じる／リロードする／回線が切れる**。
`deleteCard()` は次の順で走る。

1. `write(KEY.cards)` は素通しキーなので即座に `pushKey` → クラウドで `goal_cards` の行が消える。
   連動して `habits` と `habit_logs` は CASCADE で消え、`timeboxes.card_id` は SET NULL になる（**行は残る**）。
2. `deleteHabitsOfCard()` / `deleteTimeBoxesOfCard()` の `write` は**デバウンス対象**。
   絞り込んだ配列なので `value === null` の即送信路にも乗らず、1.5 秒待つ。

通常はこの 1.5 秒後（または `pagehide` の `flush`）に `reconcileCollection("timeboxes")` が走り、
`incomingIds` に無くなった枠を `gone` として**クラウドから delete** するので、最終的には片付く。
問題は、その前にタブが閉じた場合。`SyncBoot` の `flush` は `pushKey`（＝ supabase-js の
通常 `fetch`、`keepalive` なし・read→upsert→delete の複数往復）を呼ぶだけなので、
**閉じる瞬間には送り切れない**（`visibilitychange` の裏回しでは効くが、実際の close では届きにくい）。

**利用者への影響**

- クラウドに、`card_id`（習慣由来なら `habit_id` も）が null の `timeboxes` 行が残る。
  過去の完了枠（`review` の振り返り込み）も、未来の計画枠も対象。
- 別端末で初回同期する、または設定画面の「置き換える」で取り込むと、その孤児枠が
  localStorage に入り、**時間割・カレンダーに「目標なしの予定」として表示される**。
  ユーザーは目標もろとも予定を消したつもりなので、「消したものが戻ってきた」に見える。
- データ損失ではない（もともと消すはずだったもの）。同じ端末で再度同期が走れば
  `reconcileCollection` が孤児を消すので自己修復はする。恒久的に壊れるわけではない。
- デバウンス前は 3 つの `void pushKey` が同一 tick で発火していたので、この窓は
  「削除操作とタブ閉じの間の数十 ms」だった。**1.5 秒に広がったぶん、現実の遭遇率が上がっている**
  （「目標を消す → 済んだので閉じる」は 1.5 秒以内に十分入る）。

**修正候補**

- `deleteCard()` の末尾で `flushPendingPushes()` を呼び、削除に伴う `timeboxes` / `habits` の
  書き込みを待たせない（削除は「数が出ない・遅らせる利点がない」操作で、`value === null` を
  即送信にしているのと同じ理屈）。`storage.ts` から `sync.ts` を参照したくなければ、
  同期フック側に「このキーの次の1回はデバウンスしない」フラグを渡す口を作る。
- あるいは `push-queue` の即送信判定を「`null` または、対象キーで**要素数が減った**書き込み」まで広げる
  （削除を巻き込みで検知できる）。ただし誤検知の余地があるので、`deleteCard` 明示 flush のほうが安全。
- `SyncBoot` の close 時 flush を `navigator.sendBeacon` 相当（`keepalive`）で送れる経路にするのは
  supabase-js では難しいので、根本策は上の2つ。

**確認方法**

1. `tests/push-queue.test.mjs` に「`deleteCard` 相当の流れ（cards 即送信 → habits/timeboxes は絞り込み配列）
   のあと `pendingKeys()` が空でない」ことを示すテストを足す（現状は `gc.timeboxes` が残る）。
2. 修正後は `deleteCard` 実行直後に `pendingPushKeys()` が空になることを確認。
3. 実機（ログイン状態）：目標を削除 → 即リロード → 別プロファイル or 「置き換える」で取り込み →
   `card_id` null の枠が出ないこと。現状は出る。
