# 習慣の孤児で同期が失敗し続ける不具合を直す

日付：2026-09-14
種別：修正
状態：完了

## 結論

「目標が無い習慣」がローカルに残っている端末では、同期のたびに
`insert or update on table "habits" violates foreign key constraint
"habits_card_id_fkey"` が起き続け、画面上部に赤い帯が消えないまま残る不具合があった。
既存の自己修復（送り直し）では直せない種類の壊れ方だったため、
起動時に一度だけ走る移行（v4）でローカル側の孤児を掃除するようにした。

## 依頼と背景

竜一さんの画面に、次の帯が出続けているという報告があった。

> クラウドへの保存が止まっています。
> 同期に失敗しました（gc.habits）: insert or update on table "habits" violates
> foreign key constraint "habits_card_id_fkey" / Key is not present in table
> "goal_cards". / 23503

`habits.card_id` は目標（`goal_cards`）を指す外部キーで、参照先が無いと
Postgres が書き込みを拒否する。このアプリには「参照先が未同期なだけなら
依存順に送り直す」自己修復（[`healIfDanglingReference()`](../../src/lib/supabase/sync.ts:490)）
が既にあるが、それでも直らずに帯が出続けていた。

## 変更内容・調査結果

**観測事実**

- クラウド側の `habits_card_id_fkey` は **CASCADE**。目標を消せば、
  クラウドの習慣は自動で連鎖して消える（[2026-09-11コードレビュー](2026-09-11-前日分コードレビュー.md)より）。
- ローカル側で目標と習慣を一緒に消すのは `deleteCard()`（[storage.ts:494](../../src/lib/storage.ts:494)）
  だけで、ここを通れば整合は保たれる。
- 送信側の `pushKey()` → `reconcileCollection()` は、参照先が未同期で弾かれた場合
  `healIfDanglingReference()` が `backfillAll()`（ローカルの現状を丸ごと送り直す）で復旧を試みる。

**原因（仮説として妥当性が高いもの）**

`healIfDanglingReference()` の送り直しは「参照先はローカルにはあるが、まだ
クラウドに届いていないだけ」の場合にしか効かない。もし習慣の `cardId` が指す目標が
**ローカルの `gc.cards` にも存在しない**（過去のバージョンの不具合や、
移行前のデータ操作で `deleteCard()` を通らずに目標だけ消えた等）場合、
送り直しても同じ目標が無いままなので、`goal_cards` 側の upsert 自体が届かず、
`habits` の upsert は毎回同じ 23503 で拒否され続ける。
`noteFailure()` は復旧成功時にしか取り下げないため、帯も消えない。

この端末の実際の履歴までは追えていないが（過去ログを保存していないため）、
「ローカルにも参照先が無い習慣」が存在しさえすれば、コード上この壊れ方は
再現することを下記の検証で確認した。

**修正**

`deleteHabitsOfCard()` と同じ考え方（目標を消すときは習慣とその記録も一緒に消す）を、
起動時の移行としても適用した。

- [src/lib/storage.ts](../../src/lib/storage.ts) — `SCHEMA_VERSION` を 3 → 4 に上げ、
  移行 v4 として「`gc.cards` に無い `cardId` を持つ習慣」とその `gc.habitlogs` を削除する処理を追加

## 仕組みの説明

アプリはページを開くたびに `ensureMigrated()` を1回だけ呼ぶ。
版番号（`gc.schemaVersion`）が現在の版より低ければ、その差分だけ順番に移行関数を実行する。
今回追加した v4 は「習慣の `cardId` が、いま手元にある目標のどれとも一致しなければ削除する」
だけの単純な処理で、UUID の形を直した v3（時間割）と同じパターンを踏襲した。

移行はログイン前（同期フックが繋がる前）に走るため、掃除そのものはクラウドに影響しない。
その後ログインして同期の向きが決まったときに、既に綺麗になった状態が送られる。

## 確認したこと

| チェック | 結果 |
|---|---|
| `npm test`（全27スイート） | 通過。`storage` 63 → 67件（新規4件） |
| `npx tsc --noEmit` | エラー0 |
| `npm run build`（`next build`） | 成功 |
| ブラウザでの再現・修正確認 | 実施。下記 |

ブラウザ（`npm run dev`）で、目標1件・正常な習慣1件・**目標が存在しない孤児の習慣1件**を
`localStorage` に直接注入し、`/goals` を開き直して確認した。

- 移行後、`gc.schemaVersion` が `"4"` になった
- 孤児の習慣とその記録（`gc.habitlogs`）が消え、正常な習慣だけが残った
- 画面（`/goals`）は目標と正常な習慣を問題なく表示し、コンソールエラーは0件

## 残っていること

- この不具合を最初に生んだ経路（どの操作で「目標だけがローカルから消えた」のか）は特定できていない。
  今回の修正は結果（孤児）を掃除するもので、原因側の再発防止ではない。
  ただし調べた範囲では、現在のコードから新たに孤児が生まれる経路は見当たらなかった
  （目標を消す操作は `deleteCard()` 一本に集約されており、習慣と記録を必ず一緒に消している）。
- 竜一さんの端末での実際の帯が、今回の移行で消えることの実機確認はできていない
  （ログインとクラウドとの実通信を伴うため代行できない。R6と同じ理由）。
  ブラウザで一度 `/settings` を開き、帯が消えていること・「これでいく」を確認してもらえると確実。
