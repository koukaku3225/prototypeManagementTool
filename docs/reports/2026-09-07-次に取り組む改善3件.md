## 改善1（最優先）: UUID でない時間割IDが、時間割の同期をまるごと黙って止める

### 現在の問題

いつ・誰が・何に困るか:
**ログイン中の利用者**が、旧「次の一歩」から移行された予定を1件でも持っていると、
**時間割（`gc.timeboxes`）のクラウド保存が毎回まるごと拒否され続ける**。
本人の操作は成功して見えるので気づけず、**別端末で開いたときに「予定が空」**で初めて発覚する。
これは実際に起きた事故（`docs/reports/2026-09-06-同期が黙って止まっていた件.md`）の
「根本原因（未特定）」として同レポートの残件に明記されている。

### 根拠

- `src/lib/storage.ts:231,238` — スキーマ移行 v2 が、旧タスクを
  `id: ` + `` `from-task-${t.id}` `` という**接頭辞つきの文字列**で時間割へ変換する。
  これは Postgres の `uuid` 型として無効（`'from-task-...'::uuid` → エラーコード `22P02`
  `invalid input syntax for type uuid`）。同レポートは
  `` `'habit-abc-2026-09-06'::uuid` `` で実測再現済みと記載。
- `src/lib/supabase/mappers.ts:191` `timeBoxToRow()` は `id: b.id` を無検証で渡す。
- `src/lib/supabase/sync.ts:186-189` `reconcileCollection()` は配列を1回の
  `upsert(rows)` で送る。**1件でも不正 ID があるとバッチ全体が拒否**される。
- `src/lib/supabase/sync-decision.ts:85-94` `isForeignKeyViolation()` は
  `23503`（外部キー違反）**しか**見ていない。
- `src/lib/supabase/sync.ts:358` `healIfDanglingReference()` は
  「FK違反でなければ即 return」。つまり `22P02` は自己修復の対象外で、
  `noteFailure` に文言が残るだけで**恒久的に直らない**（移行コードが同じ ID を作り続けるため）。
- `src/lib/storage.ts:182` `SCHEMA_VERSION = 2`。v3 以降の是正マイグレーションは無い。

### 提案（最小限）

1. 純粋関数 `isValidUuid(id: string): boolean` を追加し、`tests/` に総当たりを足す。
2. スキーマ移行 **v3** を追加（`SCHEMA_VERSION = 3`）。
   `gc.timeboxes` の各要素で `isValidUuid(box.id)` が偽なら
   `crypto.randomUUID()` に置換する。時間割IDは他テーブルから参照されないので、
   ID差し替えだけで安全（`googleEventId` 等の中身は保持）。
   同時に、置換で衝突しないよう ID重複も解消する。
3. 保険として `reconcileCollection()`（または `pushKey` の timeboxes 分岐）で、
   `idColumn === "id"` のテーブルは送信前に不正 ID の行を除外し、
   除外があれば `noteFailure` で1回だけ帯に出す
   （1件の不正で他の20件が道連れになるのを防ぐ）。
4. `isForeignKeyViolation` の隣に `isInvalidUuidSyntax`（`22P02`）を用意し、
   `describeError` / 帯の文言が「IDの形式が不正」と読めるようにする（自己修復はしない）。

### 優先する理由

- **データ消失の再発防止**そのもの。中心価値（時間割で行動を管理する）が
  「別端末で予定が消える」で崩れる、実績のある事故。
- 変更は移行1本＋純粋関数＋ガード1箇所で、`npm test` で回帰を固定できる。
- カレンダー連携の完成を待つ必要がない（同期の土台の問題）。

### 完了条件

- [ ] `from-task-*` を含む `gc.timeboxes` で移行 v3 実行後、全 ID が UUID になる（冪等）。
- [ ] 不正 ID を1件含む配列を push しても、残りの行は upsert され、帯にエラーが1回出る。
- [ ] `22P02` を渡したとき、帯の文言が `[object Object]` でなく形式不正と分かる。
- [ ] 既存の同期テスト（`sync-decision` 14件ほか）が引き続き通る。

### 確認方法

- 単体: `tests/storage.test.mjs` に「`from-task-x` を含む配列 → 移行 v3 → 全UUID」
  「2回実行しても件数不変」。`tests/sync-decision.test.mjs` に
  `isValidUuid` / `isInvalidUuidSyntax` の総当たり。
- 手動: DevTools で
  `localStorage.setItem('gc.timeboxes', JSON.stringify([{...id:'from-task-1'}]))` を仕込み、
  リロード → ID が UUID 化されることを確認。ログインして `/plan` を保存 →
  設定画面と全画面帯にエラーが出ないこと、別ブラウザでログインして同じ予定が見えること。

### 規模

**中**。主対象: `src/lib/storage.ts`（移行v3）、`src/lib/supabase/sync.ts` /
`sync-decision.ts`（ガードと判定）、`tests/`。

## 改善2: 初回起動が「空の時間割」に着地し、目標対話への導線が無い

### 現在の問題

何もデータが無い利用者が初めて開くと、`/` → `/plan` にリダイレクトされ、
**24時間の空グリッドと＋ボタンだけ**が出る。このアプリの入口体験
（所要時間の明示・コーチ選択・「理想を明日の一歩に変える」の期待設定）は
`/goals` の空状態にしか無く、`BottomNav` の「目標」タブを自分で押さない限り届かない。
MVP仕様が「離脱の最大要因は"思ったより長い"」として入口の期待設定を必須にしているのに、
既定ルートがそれを迂回している。

### 根拠

- `src/app/page.tsx:14` — `/` は無条件で `redirect("/plan")`。
- `src/app/plan/page.tsx` — `ready` 後は常にグリッドを描画。データ0件の分岐なし。
- `src/components/DayGrid.tsx` — 初回向けの説明表示なし（`aria-label` のみ）。
- `src/app/goals/page.tsx:143-166` — オンボーディングCTA
  （「大きな物語をつくる」「先に直近の目標だけつくる」）は `empty` 分岐の中だけ。
- `docs/mvp-spec.md` §3.2「S1 — ランディング」= コーチ選択と所要時間明示が入口。
- `hasUserContent(captureState())` が既にある（`src/components/LocalBackupBoot.tsx:69`、
  `sync.ts`）ので、初回判定は追加コストほぼゼロ。

### 提案（最小限）

`src/app/plan/page.tsx` に、`ready` かつ
`大きな物語なし && 目標カード0件 && 実体の時間割0件 && 習慣0件` のときだけ出す
**オンボーディングカード**を1枚追加する（グリッドの上に重ねる、またはグリッドの代わり）。

- 見出し: 「あなたの"理想"を、明日の一歩に変えます」
- 所要時間の一文（仕様どおり「約30〜40分。途中で中断できます」）
- 主ボタン → `/story/new`、副リンク → `/goal/new`
- 「先に時間割だけ使う」で閉じられる（判断を奪わない）。閉じたら通常グリッド。

`/` のリダイレクト先は変えない（ブックマーク・`router.push("/")` が各所にあるため。
`page.tsx` のコメントもそう明記）。判定は client の `/plan` 側で行う。

### 優先する理由

- MVP が検証したい H1（構造化対話の価値）は、対話に**入ってもらえて初めて**測れる。
  入口を1つ増やすだけで、テスト参加者の初回離脱を直接減らせる。
- 変更は1ファイル・1コンポーネントで、既存の空状態文言を流用できる。

### 完了条件

- [ ] データ皆無の状態で `/` を開くと、対話への導線カードが見える。
- [ ] 「時間割だけ使う」を押す/1件でも予定を作ると、以後カードは出ない。
- [ ] 既存利用者（データあり）には一切表示されない。

### 確認方法

- 手動: `localStorage.clear()` → `/` を開く → カード表示を確認 → 「大きな物語をつくる」で
  `/story/new` に遷移。カードを閉じてリロード → 出ないこと。
  既存データを戻して `/plan` が従来どおりであること。
- 単体: 表示条件を純粋関数 `shouldShowOnboarding(state)` に切り出して
  `tests/` で組み合わせを固定。

### 規模

**小**。主対象: `src/app/plan/page.tsx`、必要なら小コンポーネント1つと `tests/`。

## 改善3: 振り返りの「よかった/悪かった/今後の対策」が書き捨てになっている

### 現在の問題

予定を完了すると `TimeBoxSheet` の振り返りで
「できばえ%」「よかったこと」「悪かったこと」「今後の対策
（次に同じ時間帯が来たとき、どうするか）」を書ける。
しかし**この3つの文章はどこにも再表示されない**。一覧やシートに出るのは
`できばえ%` のバッジだけ。せっかく言語化した「対策」を、
次に同種の予定を始めるときに読み返す場所が無く、
メタ認知→行動の改善ループが閉じていない。

### 根拠

- `src/components/TimeBoxSheet.tsx:431-516` `Review` が `score/good/bad/next` を保存。
- 再表示は `score` のみ: `src/app/list/page.tsx:553`、`src/components/TimeBoxSheet.tsx:308`。
- `review.good` / `review.bad` / `review.next` を読む箇所は
  「その予定を再度開いたシート内」以外に**存在しない**（grep 済み）。
- `src/components/TimeBoxSheet.tsx:258-291` はメタ認知3項目
  「始める前に決めておく」を重視する設計思想を明記。振り返り側は片肺。
- `docs/mvp-spec.md` §3 のメタ認知3問と、拡張ロードマップ「週次振り返り」も同じ方向。

### 提案（最小限）

新規画面は作らず、**既にある振り返りを1箇所で再利用**する。次のどちらか：

- **案A（小）**: 予定シート（`TimeBoxSheet`）を開いたとき、
  同じ `cardId`（または近い開始時刻）を持つ**直近の完了予定の `review.next`** を
  「前回の対策」として上部に1行表示する。始める前に自分の言葉を読み返せる。
- **案B（小〜中）**: `/me` の「続いていること」の下に
  「最近の振り返り」セクションを足し、`review.good/bad/next` が入っている
  完了予定を新しい順に5件、日付・タイトルとともに一覧する。

まず案Aを推す（行動の直前に効く。画面を増やさない）。

### 優先する理由

- 中心価値（対話で気づいた障害と対策を、実行に持ち込む）を、
  **新機能なしで**強める。データはもう溜まっている。
- 案Aは表示ロジックの追加のみで、保存経路に触れないため回帰リスクが小さい。

### 完了条件

- [ ] 過去に同じ目標の予定で「今後の対策」を書いていると、次の予定シートにそれが出る。
- [ ] 対策が未記入・過去予定なしのときは、余計な空欄を出さない。
- [ ] 既存の完了・振り返り保存の挙動は変わらない（`npm test` 通過）。

### 確認方法

- 手動: 目標Aの予定を完了し「今後の対策」に文を書く →
  同じ目標Aの別の予定を開く → その文が「前回の対策」として見える。
  対策を書かなかった場合は何も出ないこと。
- 単体: 「完了予定リスト＋対象予定 → 表示すべき対策文字列（または null）」を返す
  純粋関数を切り出し `tests/timebox.test.mjs` に追加。

### 規模

**小**（案A）。主対象: `src/components/TimeBoxSheet.tsx`、`src/lib/timebox.ts`、`tests/`。
