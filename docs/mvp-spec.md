# 目標トラッキングツール — MVP 仕様書

**バージョン**: 0.1
**作成日**: 2026-08-21
**スコープ**: 目標設定（5フェーズAI対話）＋ 目標カード生成

---

## 1. プロダクト定義

### 1.1 一文定義

> **30〜40分のAIとの対話を1回行うと、抽象的な「なりたい姿」が、意味づけされた1つの目標と、明日実行する1つの具体的タスクに変換されて手元に残る。**

### 1.2 MVPで検証する仮説

| # | 仮説 | 判定方法 |
|---|---|---|
| H1 | AIとの構造化対話は、自力でワークシートを埋めるより深い目標設定ができる | 生成された目標カードの「意味づけ」欄の記述量・具体性 |
| H2 | 「なぜ」を掘る対話は、外発的/回避的な動機を内発的動機に変換できる | フェーズ2→3で `motivation_type` が変化した割合 |
| H3 | 疑似人格への「約束」は、翌日の実行率を上げる | 約束ステップあり/なしのA/Bで翌日実行率を比較 |
| H4 | 意図的な待ち時間はユーザーの回答の質を上げる | 待ち時間あり/なしで回答文字数・具体性を比較 |

H1が偽なら、この先の記録・振り返り・リマインダー機能を作る意味がない。**MVPはH1の検証装置である。**

### 1.3 想定ユーザー

- 「何かを変えたい」という漠然とした意欲はあるが、目標に落とし込めていない社会人
- 過去に目標設定ツール・手帳を試して続かなかった経験がある
- スマホ中心で利用する

## 2. スコープ定義

### 2.1 MVPに含む

| 機能 | 概要 |
|---|---|
| コーチ選択 | 3種類の人格から1つ選ぶ |
| 5フェーズAI対話 | 発散 → 意味の掘り下げ → 動機の変換 → SMART化 → WOOP＋WBS |
| 意図的待ち時間 | フェーズ2・3のみ、送信ボタンを60秒ロック |
| 目標カード生成 | 対話内容を構造化JSONに変換し、編集可能なカードとして表示 |
| 明日の1タスク | WBSで分解した最小タスクを1件だけ提示 |
| 約束ステップ | 対話の締めに「約束」を求め、同意を記録 |
| ホーム画面 | 目標カードと明日のタスクを常設表示 |
| エクスポート | JSON / Markdown でダウンロード |
| プロフィール蓄積 | 対話から抽出した性格・生活パターンを裏で保存 |

### 2.2 MVPに含まない（意図的に除外）

| 除外するもの | 理由 |
|---|---|
| **独立した自己分析モード** | 診断を先にやらせると離脱する。対話の中に溶かして副産物として蓄積する |
| 日々の記録・週次振り返り | 目標が定まったユーザーがいないと検証不能 |
| 複数目標の優先順位づけ | MVPは1目標固定 |
| If-Thenプラン単独機能 | WOOPのPlanがIf-Thenそのもの。統合すれば新規実装ゼロ |
| プッシュ通知・ウィジェット | Web版では実装不可／検証対象外 |
| Notion連携 | Markdownエクスポートで代替 |
| 目標の依存関係グラフ | 1目標固定なので不要 |
| 音声入力 | テキストで仮説検証は可能 |
| ユーザー認証・サーバーDB | localStorage で十分 |

## 3. 画面仕様

### 3.1 画面遷移

```
[S1] ランディング
  └ コーチ選択 → [S2] 対話画面
                    └ 5フェーズ進行 → [S3] 目標カード生成・編集
                                        └ 確定 → [S4] ホーム
                                                   └ エクスポート / 対話の再開
```

すべて **モバイル幅固定**（`max-w-[420px] mx-auto`）。PCブラウザで開いても実機幅で表示される。

### 3.2 S1 — ランディング

**目的**: 期待値の設定とコーチ選択

| 要素 | 内容 |
|---|---|
| ヘッドライン | 「あなたの"なりたい姿"を、明日の一歩に変えます」 |
| サブコピー | 「AIコーチとの30分の対話で、目標が具体的な行動になります」 |
| 所要時間の明示 | 「所要時間: 約30〜40分。途中で中断できます」 |
| コーチ選択カード | 3枚（下記） |
| CTA | 「対話をはじめる」 |

**コーチ人格 3種**

| ID | 名前 | 性格 | 口調の例 |
|---|---|---|---|
| `kaede` | カエデ | 伴走型・共感重視 | 「それ、すごく大事なことだと思います。もう少し聞かせてください」 |
| `rin` | リン | 厳しめ・直球 | 「今の答え、抽象的すぎませんか。具体的にどういうことですか」 |
| `sou` | ソウ | 淡々・分析型 | 「整理すると、3つの要素がありますね。順に見ていきましょう」 |

所要時間の明示は必須。**離脱の最大要因は「思ったより長い」である。**

### 3.3 S2 — 対話画面

**レイアウト**

```
┌────────────────────────┐
│ ← カエデ    [●●●○○] 3/5 │  ← ヘッダー: コーチ名 + フェーズ進捗
├────────────────────────┤
│                        │
│  [コーチの吹き出し]      │  ← 左寄せ、ストリーミング表示
│                        │
│        [ユーザーの吹き出し] │  ← 右寄せ
│                        │
├────────────────────────┤
│ [テキスト入力欄]    [送信] │
└────────────────────────┘
```

**仕様**

- コーチの応答は **ストリーミング表示**（`client.messages.stream`）
- フェーズ番号は表示するが、フェーズ名は表示しない（構えさせないため）
- フェーズ遷移時に区切りアニメーション＋一言（例:「ここまでで、目指したい姿は見えてきましたね。次は"なぜ"を掘っていきます」）
- 中断すると localStorage に保存され、次回起動時に「続きから」ボタンが出る

**待ち時間UI（フェーズ2・3のみ）**

コーチが「なぜ」系の問いを投げたターンで発動:

```
┌────────────────────────┐
│ すぐに答えなくていいです。   │
│ 1分だけ、考えてみてください。 │
│                        │
│ ●●●●●●○○○○  42秒       │  ← カウントダウンバー
└────────────────────────┘
[入力欄は編集可能 / 送信ボタンのみ無効]
```

- 入力は**できる**が送信のみロック。考えながら書ける
- 残り時間はバーとカウントダウンで可視化
- スキップボタンは**置かない**（置くと必ず押される）
- ロック中の入力・削除の挙動を計測（`draft_events`）

### 3.4 S3 — 目標カード生成

対話完了後、構造化APIを呼び、生成中はローディング（「あなたの言葉を整理しています…」/ 想定10〜20秒）。

**カードの構成**

```
┌────────────────────────┐
│ 【なりたい姿】           │
│ 自分の判断で物事を動かせる  │
│ 状態になりたい      [編集] │
├────────────────────────┤
│ 【これが大事な理由】       │
│ ・ 誰かの許可を待つ時間が   │
│   もったいないと感じるから  │
│ ・ 「自律」が自分の核だから  │
│                  [編集] │
├────────────────────────┤
│ 【目標（SMART）】         │
│ 2026年11月30日までに、    │
│ 週2本の企画書を自主提案する │
│                  [編集] │
├────────────────────────┤
│ 【つまずきそうなこと】      │
│ 帰宅後に疲れて手が止まる     │
│  ↓ もしそうなったら         │
│ 翌朝6時に15分だけやる       │
│                  [編集] │
├────────────────────────┤
│ 【明日やること】           │
│ □ 企画書テンプレを1枚作る   │
│   （45分）                │
├────────────────────────┤
│      [これで確定する]      │
└────────────────────────┘
```

- 全項目インライン編集可能。**編集した項目は記録する**（AI出力の精度計測に使う）
- 「これで確定する」で S4 へ

### 3.5 S4 — ホーム

| 要素 | 内容 |
|---|---|
| 目標カード | S3と同じ内容を圧縮表示。タップで展開 |
| 明日やること | チェックボックス1件。チェック時刻を記録 |
| コーチからの一言 | 静的テンプレ＋目標の文言を差し込んだ短文（API呼び出しなし） |
| エクスポート | JSON / Markdown ダウンロード |
| 対話をやり直す | 確認ダイアログの上でリセット |

## 4. 5フェーズ対話仕様

### 4.1 フェーズ一覧

| # | 内部名 | ゴール | 遷移条件 | 想定ターン数 | 待ち時間 |
|---|---|---|---|---|---|
| 1 | `diverge` | 「なりたい姿」を語らせる。評価も要約もしない | ビジョンの言語化が1つ以上 | 3〜5 | なし |
| 2 | `meaning` | 「なぜそれが大事か」を3階層掘る | why_chain が3件蓄積 | 5〜8 | **あり** |
| 3 | `reframe` | 外発的/回避的動機を内発的に変換 | motivation_type 確定＋必要なら再定義に合意 | 2〜5 | **あり** |
| 4 | `smart` | いつまでに/何を/どれくらい/どうやって | SMART 4要素が埋まる | 4〜7 | なし |
| 5 | `woop_wbs` | 障害の洗い出し、If-Thenプラン、明日の1タスク | 障害1件＋プラン1件＋タスク1件 | 4〜6 | なし |

合計 **18〜31ターン**。1ターン平均60〜90秒として 30〜45分。

### 4.2 フェーズ遷移の判定

各ユーザー発言のあと、**遷移判定を対話生成と同じ1回のAPI呼び出しで行う**（追加コストなし）。応答の末尾に制御トークンを出力させ、クライアント側で剥がす。

```
（コーチの発言本文）
<<<PHASE:meaning>>>
```

`<<<PHASE:...>>>` はストリーミング中にバッファして表示から除去する。

**フォールバック**: 各フェーズに最大ターン数を設定（フェーズ1:6、2:10、3:6、4:9、5:8）。超えたらシステム側で強制遷移する。堂々巡りの防止。

### 4.3 各フェーズのAI指示

#### フェーズ1: diverge（発散）

```
ユーザーが「なりたい姿」を自由に語れる状態を作る。

やること:
- オープンな問いを1つだけ投げる
- ユーザーの言葉をそのまま受け止める
- 「それは具体的にはどういう状態ですか」と情景を聞く

やってはいけないこと:
- 要約しない。評価しない。アドバイスしない
- 「それはいい目標ですね」のような賞賛を返さない
- この段階で期限や数値を聞かない
- 複数の質問を一度に投げない
```

#### フェーズ2: meaning（意味の掘り下げ）★ 中核

```
「なぜそれが大事なのか」を3階層掘る。このアプリの価値の中心。

やること:
- 「なぜそれが大事なんですか?」を、表現を変えて3回問う
- 2回目以降は、直前のユーザーの言葉を引用して問う
  例: 「"誰かに認められたい"とおっしゃいましたね。なぜ認められることが大事なんでしょう」
- ユーザーが詰まったら、待つ。埋めようとしない
- ユーザーの言葉から価値観を表すキーワードを見つけたら、それを言い返して確認する

やってはいけないこと:
- 答えを誘導しない。「つまり◯◯ということですね?」で締めない
- 3回未満で次に進まない
- 心理学の用語（内発的動機づけ、自己決定理論など）を出さない
```

#### フェーズ3: reframe（動機の変換）

```
動機の種類を判定し、必要なら言い換えを提案する。

判定基準:
- internal（内発）: 「やりたい」「面白い」「自分にとって意味がある」
- external（外発）: 「評価されたい」「昇進のため」「認められたい」「年収」
- avoidance（回避）: 「怒られたくない」「取り残されたくない」「不安だから」

external / avoidance と判定した場合:
- 断定せず、確認する
  「今のお話を聞いていると、"評価されること"が中心にあるように聞こえました。合っていますか?」
- 合っていれば、その先を問う
  「では、評価されたその先で、何ができるようになっていたいですか?」
- ユーザーの答えから内発的な表現を一緒に作る。押しつけない
- ユーザーが「いや、評価されたいこと自体が目的です」と言えば、それを尊重して次へ

internal の場合:
- そのまま承認し、価値観の言語化を1回だけ確認して次へ
```

#### フェーズ4: smart（具体化）

```
SMARTの4要素を埋める。事務的になりすぎないよう、意味づけと繋げ続ける。

聞く順序:
1. 何を (Specific) — 「その状態に近づくために、何をしている状態が理想ですか」
2. どれくらい (Measurable) — 「それは数で表すとどれくらいですか」
3. いつまでに (Time-bound) — 「いつまでを目安にしますか」
4. どうやって (Achievable) — 「今の生活の中で、それは現実的ですか」

やること:
- 数値が曖昧なら「週1回? 毎日?」と選択肢を出して具体化を助ける
- 期限が1年以上先なら「もっと手前に、確かめられる地点を作りませんか」と提案
- 非現実的に高い目標には、根拠を1度だけ確認する

やってはいけないこと:
- 目標をユーザーの代わりに決めない
- 4要素を一度に聞かない
```

#### フェーズ5: woop_wbs（障害と行動）

```
WOOPのObstacle/Planと、明日の1タスクまで落とす。

やること:
1. 「これを続けるとして、一番つまずきそうなのはどんな時ですか」
2. 障害が出たら、それが起きる具体的な状況を特定する
   「それはどんな時間帯・どんな状況で起きますか」
3. If-Thenの形で対策を作る
   「"もし〇〇になったら、××する" の形にすると、どうなりますか」
4. 目標達成に必要な作業を3〜5個挙げさせ、その中から
   「明日、45分以内でできるもの」を1つ選ばせる
5. 最後に約束を求める（下記 §6.2）

やってはいけないこと:
- 障害を代わりに考えない。ユーザーの生活を知っているのはユーザー
- タスクを2つ以上出さない。1つに絞る
```

### 4.4 システムプロンプト構造

```
[共通コーチング原則]        ← 全フェーズ共通・不変（キャッシュ対象）
[コーチ人格定義]            ← 選択された1人格・不変（キャッシュ対象）
[ユーザープロフィール]      ← 蓄積データ。セッション内では不変（キャッシュ対象）
――― cache_control breakpoint ―――
[現在のフェーズ指示]        ← フェーズごとに差し替え
[フェーズ内で既に取得済みの情報]  ← 揮発
```

**共通コーチング原則（抜粋）**

```
あなたはコーチであり、コンサルタントでもセラピストでもない。

- 答えはユーザーの中にある。あなたは問うだけ
- 1つの発言につき、質問は1つだけ
- ユーザーの言葉をあなたの言葉に置き換えない。そのまま使う
- 沈黙を埋めない。短い返答でも催促しない
- 助言をしたくなったら、代わりに問いにする
- 1発言は3文以内。長い説明をしない
- 診断名や心理学用語を使わない
- ユーザーが answer した内容を否定しない
```

## 5. データモデル

`src/types/goal.ts`

```typescript
export type MotivationType = "internal" | "external" | "avoidance";
export type PhaseId = "diverge" | "meaning" | "reframe" | "smart" | "woop_wbs";
export type CoachId = "kaede" | "rin" | "sou";

/** 対話から生成される最終成果物 */
export interface GoalCard {
  id: string;
  createdAt: string;              // ISO8601
  updatedAt: string;
  coachId: CoachId;

  vision: {
    raw: string;                  // ユーザーが最初に語った生の言葉
    refined: string;              // 対話を経て磨かれた表現
  };

  meaning: {
    whyChain: string[];           // 「なぜ」3階層の答え
    values: string[];             // 抽出された価値観キーワード
    motivationType: MotivationType;
    reframed: string | null;      // 変換後の表現（変換した場合のみ）
    reframedFrom: string | null;  // 変換前の表現
  };

  smart: {
    specific: string;
    measurable: string;           // 「週2本の企画書」
    metricUnit: string | null;    // 「本」
    metricTarget: number | null;  // 2
    deadline: string;             // ISO8601 date
    achievableNote: string;       // 実現可能性についての本人の言葉
  };

  woop: {
    wish: string;
    outcome: string;              // 達成したときに得られる状態
    obstacles: Obstacle[];
  };

  tasks: Task[];                  // MVPでは常に1件

  commitment: {
    accepted: boolean;
    acceptedAt: string | null;
    userWords: string | null;     // ユーザーが実際に打った同意の言葉
  };
}

export interface Obstacle {
  id: string;
  text: string;                   // 「帰宅後に疲れて手が止まる」
  situation: string;              // 「平日21時以降、帰宅直後」
  plan: {
    if: string;                   // 「21時に机に座れなかったら」
    then: string;                 // 「翌朝6時に15分だけやる」
  };
}

export interface Task {
  id: string;
  title: string;
  estimateMin: number;
  dueDate: string;                // ISO8601 date
  completedAt: string | null;
}

/** 対話から裏で抽出され、次回以降の対話品質を上げる */
export interface UserProfile {
  updatedAt: string;
  lifePatterns: string[];         // 「平日は22時帰宅」「朝は弱い」
  pastFailures: string[];         // 「3日坊主になりがち」
  valuesAccumulated: string[];    // 全セッションを通じた価値観
  communicationStyle: {
    avgResponseLength: number;
    prefersConcrete: boolean;     // 抽象的な問いに詰まる傾向か
  };
}

/** 対話セッションの状態（中断復帰に使う） */
export interface Session {
  id: string;
  coachId: CoachId;
  currentPhase: PhaseId;
  phaseTurnCounts: Record<PhaseId, number>;
  messages: ChatMessage[];
  startedAt: string;
  completedAt: string | null;
  variant: ExperimentVariant;     // A/Bテスト割り当て
}

export interface ChatMessage {
  role: "user" | "assistant";
  content: string;
  phase: PhaseId;
  timestamp: string;
  /** 待ち時間中の入力挙動（H4検証用） */
  draftEvents?: {
    lockDurationMs: number;
    charsTyped: number;
    charsDeleted: number;
    firstKeystrokeAtMs: number;   // ロック開始からの経過
  };
}

export interface ExperimentVariant {
  commitmentStep: boolean;        // H3: 約束ステップ
  deliberateDelay: boolean;       // H4: 意図的待ち時間
}
```

## 6. AI実装仕様

### 6.1 モデル選定

**2段構え**にする。対話は安いモデル、判断が要る構造化は上位モデル。

| 用途 | モデルID | 1セッションの呼び出し回数 | 選定理由 |
|---|---|---|---|
| 対話の各ターン | `claude-haiku-4-5` | 18〜31 | 「次の問いを1つ返す」だけなら十分。$1/$5 per MTok と最安 |
| 構造化抽出（GoalCard生成） | `claude-sonnet-5` | 1 | 対話全体を読んで正確なJSONにする。判断精度が要る |
| 動機タイプの判定・変換提案 | `claude-sonnet-5` | 1〜2 | 誤判定するとフェーズ3全体が崩れる |
| プロフィール抽出 | `claude-sonnet-5` | 1 | 構造化抽出と同一呼び出しに統合可 |

**参考価格**（Anthropic API 一次価格 / 1M tokens）

| モデル | Input | Output | コンテキスト |
|---|---|---|---|
| `claude-haiku-4-5` | $1.00 | $5.00 | 200K |
| `claude-sonnet-5` | $3.00（2026-08-31まで導入価格 $2.00） | $15.00（同 $10.00） | 1M |
| `claude-opus-5` | $5.00 | $25.00 | 1M |

対話品質が不足した場合は、フェーズ2・3だけ `claude-sonnet-5` に上げる。それでも足りなければ `claude-opus-5`。**まずHaikuで始めて、質が足りない箇所だけ上げるのが正しい順序。**

### 6.2 1セッションあたりのコスト試算

対話（Haiku 4.5、プロンプトキャッシュあり）:
- 入力: 25ターン × 平均4,000トークン = 100K（うち約70%がキャッシュヒット）
- 出力: 25ターン × 200トークン = 5K
- 概算: **約$0.06**

構造化（Sonnet 5、導入価格）:
- 入力: 2回 × 10K = 20K、出力: 2回 × 2K = 4K
- 概算: **約$0.08**

**合計 約$0.14 / セッション（≒ 20〜25円）**。100人にテストしても2,500円程度。プロトタイプとして十分に許容範囲。

### 6.3 API設計

```
POST /api/chat        対話1ターン。SSEストリーミング。Haiku 4.5
POST /api/structure   対話全体 → GoalCard JSON。Sonnet 5
POST /api/profile     対話全体 → UserProfile。/api/structure に統合してもよい
```

**`/api/chat` の実装方針**

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();  // ANTHROPIC_API_KEY を環境から解決

const stream = client.messages.stream({
  model: "claude-haiku-4-5",
  max_tokens: 1024,              // コーチの発言は3文以内。小さく抑える
  system: [
    // 不変部分をキャッシュ対象にする（順序を固定すること）
    { type: "text", text: COACHING_PRINCIPLES },
    { type: "text", text: COACH_PERSONAS[coachId] },
    {
      type: "text",
      text: renderProfile(profile),
      cache_control: { type: "ephemeral" },   // ← ここまでをキャッシュ
    },
    { type: "text", text: PHASE_INSTRUCTIONS[currentPhase] },
  ],
  messages: history,
});

for await (const event of stream) {
  if (event.type === "content_block_delta" && event.delta.type === "text_delta") {
    // <<<PHASE:xxx>>> をバッファして除去してからクライアントへ送る
    push(filterControlToken(event.delta.text));
  }
}
```

**キャッシュの注意**: `cache_control` はプレフィックス一致。システムプロンプトに時刻や乱数を混ぜると毎回失効する。`usage.cache_read_input_tokens` が0のままなら、どこかに揮発値が紛れている。

**`/api/structure` の実装方針**

構造化出力は Zod スキーマ + `client.messages.parse()` を使う。

```typescript
import { z } from "zod";
import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod";

const GoalCardSchema = z.object({
  vision: z.object({ raw: z.string(), refined: z.string() }),
  meaning: z.object({
    whyChain: z.array(z.string()),
    values: z.array(z.string()),
    motivationType: z.enum(["internal", "external", "avoidance"]),
    reframed: z.string().nullable(),
    reframedFrom: z.string().nullable(),
  }),
  smart: z.object({ /* ... */ }),
  woop: z.object({ /* ... */ }),
  tasks: z.array(z.object({ /* ... */ })),
});

const response = await client.messages.parse({
  model: "claude-sonnet-5",
  max_tokens: 16000,
  system: STRUCTURE_EXTRACTION_PROMPT,
  messages: [{ role: "user", content: renderTranscript(session.messages) }],
  output_config: { format: zodOutputFormat(GoalCardSchema) },
});

// parsed_output は失敗時 null。必ずガードする
if (!response.parsed_output) throw new StructureExtractionError();
```

**抽出プロンプトの原則**

```
対話ログから情報を抽出する。あなたの役割は記録係であり、創作者ではない。

- ユーザーが実際に言った言葉を可能な限りそのまま使う
- ユーザーが言っていないことを補完しない
- 情報が不足している項目は、推測せず null にする
- refined は raw の言い換えであり、内容を追加してはいけない
```

**「言っていないことを書かない」が最重要。** AIが勝手に立派な目標を作ると、ユーザーは自分の目標だと感じられなくなり、H1の検証が汚染される。

### 6.4 エラー処理

| ケース | 挙動 |
|---|---|
| ストリーミング中の切断 | 直前のユーザー発言を保持し「もう一度送る」ボタンを出す |
| `parsed_output` が null | 1回だけリトライ。再失敗なら対話ログをそのまま表示し、手入力での作成を促す |
| レート制限 (429) | SDKの自動リトライに任せる（`maxRetries` 既定2）。UIには「少し混み合っています」 |
| APIキー未設定 | 起動時に検出し、開発者向けエラーを表示 |
| localStorage 書き込み失敗 | try/catch。失敗時は「保存できませんでした。エクスポートしてください」 |

エラーハンドリングは SDK の型付き例外クラスで分岐する（`Anthropic.RateLimitError` など）。文字列マッチはしない。

## 7. 疑似人格と待ち時間の仕様

### 7.1 疑似人格（H3の検証装置）

MVPでは以下の3点のみ実装する。これで「人格がいる」と感じさせるのに足りる。

**① 名前と口調の固定**
選択したコーチのシステムプロンプトを全ターンで固定。途中で変えない。

**② 過去の発言の引用**
`UserProfile` をシステムプロンプトに含め、以下を指示する。

```
ユーザーが過去に語った内容が [ユーザープロフィール] にある場合、
自然な形で1セッションに1〜2回だけ引用する。
例:「前に"時間がない"とおっしゃっていましたね」
毎回引用すると不自然になる。使いすぎないこと。
```

**③ 約束ステップ**（A/Bテスト対象）

フェーズ5の最後:

```
コーチ: 「じゃあ最後に一つ。明日、"企画書テンプレを1枚作る"。
        これ、私に約束してくれますか?」

[入力欄]  ← ユーザーが自分で言葉を打つ。ボタンではない
```

**ボタンではなくテキスト入力にすることが要点。** 自分の言葉で書かせることでコミットメントが強くなる。打たれた言葉は `commitment.userWords` に保存し、翌日ホーム画面で再提示する。

`variant.commitmentStep === false` の群では、このステップを飛ばして「では、明日がんばってください」で終える。

### 7.2 意図的待ち時間（H4の検証装置）

**発動条件**: `variant.deliberateDelay === true` かつ現在フェーズが `meaning` または `reframe` かつコーチの発言が問いで終わっている。

**仕様**

| 項目 | 値 |
|---|---|
| ロック時間 | 60秒 |
| ロック対象 | 送信ボタンのみ（入力欄は編集可能） |
| スキップ | 不可（ボタンを置かない） |
| 表示 | カウントダウンバー＋残り秒数 |
| 計測 | `draftEvents`（打鍵数、削除数、最初の打鍵までの時間） |

**全フェーズに適用してはいけない。** 事務的なフェーズ4・5で待たせると苛立ちしか生まない。深さが要る2フェーズに限定する。

**将来の拡張案（MVP対象外）**: 目標カードの確定を24時間ロックし、翌日「まだこれで良いですか?」と再確認する。検証サイクルが遅くなるためMVPには含めない。

## 10. 検証指標
