# 作業後のMarkdown解説

## 目的と適用

ユーザーの実装・修正・調査依頼を終えたら、会話を読んでいない本人にも「何が分かったか／何が変わったか／なぜそうしたか」が伝わる日本語のMarkdownを保存する。小さな修正、原因未確定の調査、設定・スキルの変更も対象。

単なる挨拶・進捗質問への回答だけでは作らない。ユーザーが明示的に文書不要と指定した場合はその指示に従う。作業を続けている途中の各ツール実行ごとには作らず、一つの依頼の成果物としてまとめる。

## 保存ルール

- 既定はリポジトリ直下の `docs/reports/YYYY-MM-DD-短い内容.md`。日付はユーザーのローカル日付を使う。
- 別の依頼は別ファイル。同日・同名が存在したら内容を確認し、別件なら `-02` などで衝突を避ける。同じ依頼の継続は既存報告を更新する。
- ユーザー指定の出力先があれば優先する。
- 依頼そのものが設計書・調査報告書などのMarkdown作成なら、その文書に下記の必須情報を含めれば報告を兼ねられる。重複した報告を増やさない。
- 参考例のMCP設計書に毎回追記しない。MCP固有の章構成や技術を他の仕事に持ち込まない。

## 手順

1. 本来の依頼と必要な検証を進め、確認済みの事実・未確認事項・変更ファイルを整理する。
2. 以下の構成でMarkdownを書く。小さな修正は短い段落で十分。大きな実装は仕組み、選択肢、運用上の制約も説明する。
3. 保存後に読み返し、実際の差分・検証結果と照合する。ファイルの存在、リンク先、コードフェンス、残った仮置き文言を確認する。
4. 最終回答に、結論とMarkdownの絶対パスリンクを載せる。

追加の承認を求める工程ではない。文書を作るためだけに本来の作業を止めたり、未依頼の実装・コミット・公開を行ったりしない。報告の生成・修正自体について、さらに報告を再帰的に作らない。

## 必須の構成

```markdown
# 具体的な作業名

日付：YYYY-MM-DD
種別：実装／修正／調査／設計
状態：完了／一部完了／調査継続が必要

## 結論

何ができるようになったか、または何が分かったかを先に書く。

## 依頼と背景

何を解決したかったか。修正なら元の症状と発生条件。

## 変更内容・調査結果

変更前後、採用した方法と理由。調査なら観測事実・仮説を区別する。
コードを変更していなければ、そのことを明記する。

## 仕組みの説明

ユーザーの操作から結果までを平易に説明する。専門用語はその場で補足。
複雑な流れに限ってMermaidや表を使う。

## 関連ファイル・根拠

変更したファイルや判断の根拠へのリンクと、それぞれの役割。

## 確認したこと

実施した検証と結果。未実施なら理由を書く。
テスト未実施、実環境未確認、仮説を成功扱いしない。

## 残っていること

制約、未確認事項、次に必要な行動。残件なしならその旨を記す。
```

実装済みと設計案を明確に分ける。設計では動作試験の代わりに「設計の確認範囲」と「実装後の受入条件」を記載してよい。全ての仕事を長い設計書にする必要はないが、必須情報は短い仕事でも残す。

## 記述の品質

- 結論から説明し、ツールを実行した順番の実況にしない。
- 「何を変更したか」と「本人にとって何が変わるか」を結びつける。
- 実在するファイルには検証済みのリンクを付ける。文書内はリポジトリ相対リンク、最終回答は絶対パスリンクを使う。
- 外部仕様を調べた場合は主張の近くに公式資料のURLを付ける。
- 秘密鍵、トークン、個人の対話全文や実データを転記しない。例が必要なら架空と明記する。
- 原因を確定できない調査は「確認できた事実」「原因候補」「次に確かめること」を記載する。

例：ボタン文言だけの変更でも、変更前後と目的、対象ファイル、実際に確認したことを短くまとめ、`docs/reports/YYYY-MM-DD-button-label.md`へ保存する。チャットの完了報告だけで終えない。
